# Python、PyQt、前端与 AI 编程能力面试题库

## 一、使用说明

本文供面试官按候选人经历自由抽题，不建议逐题询问。适用于 Python Web 后端工程师，以及具有 PyQt 桌面开发经验、能承担一定前端工作的综合型候选人。

难度标记：

- **初级**：验证语言和框架基础是否准确，能否完成边界明确的任务。
- **中级**：验证真实项目开发、调试、并发和工程实践能力。
- **高级**：验证架构设计、复杂故障治理、跨端协作和技术决策能力。

建议一次面试选题方式：

1. Python 语言基础：3 至 5 题。
2. 并发、异步与性能：2 至 4 题。
3. Web 后端：3 至 5 题。
4. PyQt 桌面开发：4 至 6 题。
5. 爬虫与数据采集：2 至 4 题；涉及真实采集项目时增加数据治理和合规追问。
6. 逆向分析与协议理解：2 至 4 题；只讨论已授权软件、内部系统或公开样本。
7. 数据库、系统设计与工程实践：3 至 5 题。
8. 前端能力：2 至 3 题。
9. AI 编程工具：2 至 3 题。
10. 项目核验、编码或设计题：至少 1 项。

如果岗位以桌面端为主，应增加 PyQt 现场排障题；如果岗位以 Web 后端为主，仍建议至少询问事件循环、线程和打包发布，以核验候选人声称的桌面开发经验。

开放题不要求候选人与参考答案逐字一致。重点判断其是否能说明原理、适用边界、风险和验证方式。

## 二、通用评分尺度

每道题可按 0 至 4 分记录：

- **0 分**：不了解，或回答与事实明显冲突。
- **1 分**：记得术语，但无法解释原理和实际用法。
- **2 分**：基础正确，能完成常规开发，但缺少边界意识。
- **3 分**：能结合项目解释取舍、风险、排障和验证方法。
- **4 分**：能从系统、用户体验、团队协作和长期维护角度提出完整方案，并识别隐含问题。

综合判断时重点关注：

- 是否理解 Python 动态特性带来的便利和风险。
- 是否能正确选择同步、线程、进程和协程模型。
- 是否理解 Web 请求、桌面事件循环与后台任务的数据流。
- 是否重视事务、幂等、资源释放、错误边界和发布质量。
- 爬虫候选人是否重视授权、限速、增量、去重、数据质量和可恢复性。
- 逆向分析候选人是否先确认范围、保留证据、结合静态与动态事实，并能把发现转化为工程改进。
- 使用 AI 工具时是否具备独立审查、事实核验和测试闭环。

## 三、Python 语言基础

### 1. Python 中可变对象和不可变对象有什么区别

**难度：** 初级

**问题：** 请举例说明可变与不可变对象。函数参数传递时，为什么修改列表内容会影响调用方，而重新给参数赋值不会？

**考察点：** 对象模型、名称绑定、可变性。

**参考答案：**

- Python 变量是对对象的名称绑定，不是装对象的固定盒子。
- `list`、`dict`、`set` 通常可变；`int`、`str`、`tuple` 通常不可变，但元组内部仍可能引用可变对象。
- 调用函数时传递的是对象引用。对列表执行 `append` 会修改同一对象，调用方可见；给形参重新赋值只是改变函数局部名称的绑定。
- 可变共享状态会增加副作用和并发复杂度，接口应明确是否原地修改。

**深入追问：** `tuple` 是否一定能作为字典 key？

**评分要点：** 必须指出元组元素也需要可哈希；包含列表的元组不可哈希。

### 2. 为什么不应使用可变对象作为默认参数

**难度：** 初级

**问题：** 下面这类定义有什么问题：`def add_item(item, items=[]): ...`？

**考察点：** 函数定义时求值、共享状态。

**参考答案：**

- 默认参数在函数定义时求值一次，而不是每次调用时重新创建。
- 多次调用会共享同一个列表，导致数据意外累积。
- 通常使用 `None` 作为哨兵，在函数内部创建新列表。
- 如果确实需要共享缓存，应显式表达并考虑线程安全，而不是借默认参数隐藏状态。

**深入追问：** `None` 本身也可能是合法业务参数时怎么办？

**评分要点：** 可使用模块级唯一哨兵对象，例如 `_MISSING = object()`，区分“未提供”和“明确传入 None”。

### 3. 浅拷贝和深拷贝有什么区别

**难度：** 初级至中级

**问题：** `copy.copy`、`copy.deepcopy` 和列表切片分别会复制什么？

**考察点：** 嵌套对象、性能和副作用。

**参考答案：**

- 浅拷贝创建新的外层容器，但内部元素仍引用原对象。
- 深拷贝递归复制对象图，通常会处理循环引用，但可能成本较高，也不一定适合文件句柄、锁、数据库连接等资源对象。
- 列表切片或 `list(old)` 通常是浅拷贝。
- 不应把 `deepcopy` 当作通用隔离方案，应优先设计清晰的数据所有权和不可变结构。

**深入追问：** 为什么对 ORM 实体或 PyQt 控件做深拷贝通常不合理？

**评分要点：** 应提到会话状态、底层 C++ 对象、父子关系和外部资源无法简单复制。

### 4. 迭代器和生成器解决了什么问题

**难度：** 中级

**问题：** 可迭代对象、迭代器和生成器分别是什么？处理大文件时为什么常用生成器？

**考察点：** 惰性计算、协议理解。

**参考答案：**

- 可迭代对象能返回迭代器；迭代器实现 `__iter__` 和 `__next__`，逐项产生值并以 `StopIteration` 结束。
- 生成器是创建迭代器的便捷方式，函数执行到 `yield` 时暂停并保留局部状态。
- 惰性处理可以减少峰值内存，并允许流水线处理大数据。
- 生成器通常只能消费一次，异常和资源关闭时机也需要明确。
- 读取文件时应结合上下文管理器，避免生成器尚未消费完时文件生命周期不清晰。

**深入追问：** 把生成器直接返回给已经结束的 `with open(...)` 外部消费，会有什么问题？

**评分要点：** 文件可能已经关闭；应让资源生命周期覆盖迭代过程，或封装为生成器内部的上下文。

### 5. 装饰器和闭包如何工作

**难度：** 中级

**问题：** 装饰器适合解决什么问题？为什么通常要使用 `functools.wraps`？

**考察点：** 高阶函数、元数据和横切关注点。

**参考答案：**

- 装饰器接收函数或类并返回包装后的对象，可用于日志、权限、缓存、重试和注册等横切能力。
- 闭包能捕获外层作用域变量，带参数装饰器通常由多层函数构成。
- `functools.wraps` 保留原函数名称、文档、注解和 `__wrapped__`，便于调试、反射和框架识别。
- 装饰器不应隐藏复杂副作用或改变调用契约却不更新类型和文档。
- 异步函数需要异步包装器，不能用普通同步包装器错误地处理 coroutine。

**深入追问：** 一个重试装饰器需要避免重试哪些异常？

**评分要点：** 业务校验失败和不可恢复错误通常不应重试；应按异常类型、幂等性、次数和退避策略设计。

### 6. 上下文管理器的作用是什么

**难度：** 中级

**问题：** `with` 语句除了关闭文件，还适合管理哪些资源？

**考察点：** 资源生命周期、异常安全。

**参考答案：**

- 上下文管理器通过 `__enter__`、`__exit__` 或 `contextlib.contextmanager` 表达资源获取与释放边界。
- 适合数据库事务、锁、临时目录、计时、日志上下文和可撤销状态。
- 即使代码抛异常，退出逻辑仍会执行；`__exit__` 是否返回真值决定是否抑制异常。
- 异步资源使用 `async with` 和异步上下文管理协议。
- 不应无意中吞掉异常，资源释放失败也需要有明确处理方式。

**深入追问：** 数据库事务上下文中，业务代码异常时应该如何处理？

**评分要点：** 通常回滚并重新抛出或转换异常，不能回滚后静默返回成功。

### 7. `__getattr__`、`__getattribute__` 和描述符有什么区别

**难度：** 高级

**问题：** Python 属性访问可以被哪些机制控制？ORM 字段为什么常使用描述符？

**考察点：** 数据模型、框架原理。

**参考答案：**

- `__getattribute__` 拦截几乎所有实例属性访问，错误实现容易无限递归。
- `__getattr__` 只在常规查找失败后调用，适合动态兜底。
- 描述符通过 `__get__`、`__set__`、`__delete__` 控制类属性绑定到实例时的行为。
- 数据描述符通常优先于实例字典，可实现校验、懒加载和 ORM 字段代理。
- 元编程能力应谨慎使用，业务代码优先选择显式、可读的数据结构。

**深入追问：** `property` 与描述符是什么关系？

**评分要点：** `property` 本身就是一种描述符，为 getter、setter 和 deleter 提供封装。

### 8. 类型标注能提供什么保障

**难度：** 中级

**问题：** Python 有类型标注后，运行时就能阻止传入错误类型吗？

**考察点：** 静态检查、运行时边界。

**参考答案：**

- 类型标注默认不会在运行时强制检查，主要服务于 IDE、静态检查器、文档和框架元数据。
- `mypy`、Pyright 等工具能在开发阶段发现部分类型错误，但无法证明业务正确。
- Pydantic 等库可以在运行时解析和校验外部数据，但这属于框架行为，不是注解本身的保证。
- 应优先标注公共接口和核心数据模型，避免用大量 `Any` 使检查失效。
- 类型设计应表达可空、联合、协议和泛型边界，而不是只追求覆盖率数字。

**深入追问：** 什么时候使用 `Protocol` 比继承抽象基类更合适？

**评分要点：** 当希望基于结构化子类型描述能力、降低实现耦合时适合；运行时行为需另行确认。

### 9. Python 包、模块和依赖如何管理

**难度：** 中级

**问题：** 如何避免“在我的电脑上能运行，部署后找不到模块或版本冲突”？

**考察点：** 环境隔离、可重复构建。

**参考答案：**

- 使用独立虚拟环境，不依赖系统 Python 的全局包。
- 在 `pyproject.toml` 等项目元数据中声明直接依赖，并使用锁文件或受控版本策略保证可重复安装。
- 明确项目包结构和启动入口，避免依赖当前工作目录或随意修改 `sys.path`。
- 区分开发、测试和生产依赖，CI 从干净环境构建验证。
- 对包含本地扩展的包，需要考虑 Python 版本、操作系统、CPU 架构和 wheel 可用性。

**深入追问：** 为什么只保存一次 `pip freeze` 也可能不够？

**评分要点：** 它混合直接与间接依赖，未必表达跨平台条件、构建工具和更新策略；仍需项目元数据与受控锁定流程。

## 四、并发、异步与性能

### 10. GIL 对线程有什么影响

**难度：** 中级

**问题：** Python 有 GIL 是否意味着线程完全没有用？

**考察点：** CPython 执行模型、任务分类。

**参考答案：**

- 在传统 CPython 构建中，GIL 通常限制同一进程内多个线程同时执行 Python 字节码。
- I/O 等待期间线程可以切换，因此线程仍适合网络、文件等 I/O 密集任务。
- CPU 密集的纯 Python 代码通常需要多进程、本地扩展、向量化或其他运行时方案获得多核并行。
- 某些 C 扩展会释放 GIL，实际表现不能只凭任务名称判断。
- 新版本可能提供可选的 free-threaded 构建，但生态兼容、性能和线程安全仍需按实际运行环境验证，不能假设部署环境已无 GIL。

**深入追问：** 为什么“使用多线程后 CPU 仍只有一个核心接近满载”可能是合理现象？

**评分要点：** 能联系纯 Python CPU 密集任务和传统 GIL 行为，并提出用测量验证。

### 11. 线程、进程和协程如何选择

**难度：** 中级

**问题：** 请分别给出适用场景和主要风险。

**考察点：** 并发模型、资源成本。

**参考答案：**

- 线程适合阻塞 I/O 和与只提供同步 API 的库集成，但共享状态需要同步。
- 进程适合 CPU 密集或需要故障隔离的任务，但启动、序列化、内存和进程间通信成本更高。
- 协程适合大量可异步等待的 I/O，用较少线程管理高并发连接，但要求整个调用链避免阻塞事件循环。
- 选择还受库支持、任务持续时间、取消需求、部署平台和可观测性影响。
- 混合模型很常见，例如异步 Web 服务把 CPU 任务提交给进程池或任务队列。

**深入追问：** 一个异步接口中调用同步数据库驱动会怎样？

**评分要点：** 会阻塞事件循环并影响同进程其他请求；可改用异步驱动、线程池隔离或同步部署模型。

### 12. `asyncio` 事件循环如何工作

**难度：** 中级

**问题：** `async def` 被调用后是否立即执行？`await` 的作用是什么？

**考察点：** coroutine、调度和非阻塞。

**参考答案：**

- 调用 `async def` 通常得到 coroutine 对象，不会像普通函数一样完整执行。
- coroutine 被 await、创建为 task 或由事件循环运行后才推进。
- `await` 在等待可等待对象时让出控制权，使事件循环调度其他就绪任务。
- 如果协程内部执行长时间 CPU 计算或同步阻塞调用，即使写了 `async` 也会卡住事件循环。
- task 的异常需要被等待或收集，否则可能出现未处理异常告警或静默失败。

**深入追问：** `asyncio.create_task` 后不保存引用有什么风险？

**评分要点：** 生命周期、异常收集和应用关闭时取消难以管理；应纳入明确任务集合或结构化并发边界。

### 13. 异步任务的取消和超时如何设计

**难度：** 高级

**问题：** 用户取消请求或服务准备关闭时，正在运行的协程应该如何响应？

**考察点：** 取消语义、资源清理。

**参考答案：**

- 取消通常在 `await` 点以取消异常传播，代码不能用宽泛异常捕获后无意吞掉。
- 使用 `try/finally` 或异步上下文管理器释放连接、锁和临时资源。
- 超时应设置在合适层级，区分单个下游超时和整体请求预算。
- 对不能中断的外部副作用，需要通过幂等、状态查询或补偿确认最终结果，不能把本地超时等同于下游失败。
- 服务优雅关闭时停止接收新任务，等待有限时间，再取消并记录未完成任务。

**深入追问：** HTTP 调用本地超时后，能否确定对方没有成功处理？

**评分要点：** 不能；请求可能已到达并执行，需要幂等键和结果查询机制。

### 14. Python 服务内存持续增长如何排查

**难度：** 高级

**问题：** 一个长期运行的 Python 服务 RSS 持续上升，你会如何判断是泄漏、缓存还是分配器行为？

**考察点：** 性能证据、对象生命周期。

**参考答案：**

1. 关联流量、任务、发布时间和进程数量，确认增长模式与影响。
2. 区分 Python 堆对象增长、C 扩展内存、文件映射和分配器未归还操作系统。
3. 使用 `tracemalloc`、对象统计、采样分析或堆分析比较时间点快照。
4. 检查无界缓存、全局集合、闭包、任务引用、循环引用、未关闭响应或 Qt 对象等。
5. 用最小负载复现并一次改变一个变量，修复根因后观察稳定基线。
6. 进程定期重启可以止损，但不能替代根因分析。

**深入追问：** Python 对象数量下降后 RSS 为什么不一定立即下降？

**评分要点：** 内存分配器可能保留 arena 供后续复用，碎片和 C 扩展行为也会影响 RSS。

## 五、Python Web 后端

### 15. FastAPI、Django 和 Flask 如何选择

**难度：** 中级

**问题：** 不要只比较性能，请从项目职责和团队角度说明选择依据。

**考察点：** 框架边界、技术决策。

**参考答案：**

- Django 提供 ORM、管理后台、认证等完整能力，适合希望统一约定和快速构建完整业务系统的团队。
- FastAPI 强调类型驱动、OpenAPI 和异步能力，适合 API 服务，但数据库、任务和权限等仍需选择并治理。
- Flask 核心轻量、自由度高，适合简单服务或团队有成熟组件规范的场景，但大型项目容易因缺少约束而风格分散。
- 选择还要考虑团队经验、依赖生态、维护年限、同步/异步调用链和部署模式。
- 不应仅根据微基准决定业务系统框架。

**深入追问：** 已有大型 Django 单体是否应该为了异步全部迁移 FastAPI？

**评分要点：** 应先识别真实瓶颈和边界，可局部拆分或优化；全面迁移成本与风险需要量化。

### 16. 依赖注入和中间件分别适合做什么

**难度：** 中级

**问题：** 在 FastAPI 等框架中，认证、数据库会话和业务服务应放在哪里？

**考察点：** 请求边界、职责分离。

**参考答案：**

- 中间件适合所有或大部分请求都需要的协议级处理，如 trace、耗时、基础安全头和统一上下文建立。
- 依赖注入适合路由级的认证、数据库会话、租户上下文和服务组装，可组合且易测试。
- 业务规则不应堆在中间件或路由函数中，应进入用例或领域服务。
- 数据库会话生命周期要覆盖一次请求或明确事务单元，并在异常时关闭或回滚。
- 中间件顺序会影响异常、CORS、日志和响应处理，必须有集成测试验证。

**深入追问：** 为什么把权限判断只写在前端或路由装饰器名称里不够？

**评分要点：** 必须有实际后端资源级授权，并确保所有入口都经过同一策略。

### 17. Pydantic 模型、ORM 模型和领域对象是否应该共用

**难度：** 中级至高级

**问题：** 一个模型贯穿接口、数据库和业务层看起来很省事，有什么风险？

**考察点：** 数据边界、耦合控制。

**参考答案：**

- API 模型表达外部契约，ORM 模型表达持久化结构，领域对象表达业务不变量，变化原因并不相同。
- 完全共用容易泄漏内部字段、让数据库结构绑死 API，并使业务逻辑依赖 ORM 会话状态。
- 小型 CRUD 项目可适度复用，但敏感字段、写入模型和返回模型至少应区分。
- 转换代码不应机械复制散落各处，可集中在明确的 mapper 或用例边界。
- 重点不是“必须三套类”，而是防止职责和信任边界混在一起。

**深入追问：** 用户更新接口为什么不应直接接收完整数据库实体？

**评分要点：** 可能造成越权字段写入、质量差的部分更新语义和内部结构泄漏。

### 18. 同步接口和异步接口如何部署

**难度：** 高级

**问题：** FastAPI 中把所有路由都改成 `async def` 是否一定提高吞吐？

**考察点：** 调用链、服务器模型。

**参考答案：**

- 只有调用链中的等待可以非阻塞时，异步才能有效利用事件循环。
- `async def` 内调用同步阻塞库会直接阻塞事件循环，可能比同步路由更差。
- 同步路由通常由框架放在线程池执行，但线程池和连接池也有容量上限。
- CPU 密集任务不应直接占用请求 worker，应交给进程池或后台任务系统。
- 部署需要结合 worker 数量、每进程连接数、数据库池、超时和容器资源压测。

**深入追问：** 数据库连接池大小是否应该等于最大并发请求数？

**评分要点：** 不应机械相等；需考虑数据库容量、事务占用时间、worker 数量和排队策略。

### 19. 如何统一处理 API 错误

**难度：** 中级

**问题：** 参数校验、业务失败和系统异常分别应如何返回？

**考察点：** 错误契约、安全和可观测性。

**参考答案：**

- 框架校验负责输入格式和基本约束，业务层返回或抛出稳定的领域错误。
- 统一异常处理器将错误映射为 HTTP 状态、业务错误码、安全消息和 trace ID。
- 系统异常的详细堆栈记录在服务端，不向客户端暴露 SQL、路径、密钥和内部结构。
- 不应使用宽泛 `except Exception: return success`，也不应在每层重复记录同一堆栈。
- 错误响应需要兼顾前端字段提示、重试判断和监控聚合。

**深入追问：** 什么时候返回 409，而不是 400？

**评分要点：** 当请求格式合法但与当前资源状态冲突，例如版本冲突、重复资源或状态不允许。

### 20. Web 认证和多租户隔离如何实现

**难度：** 中级至高级

**问题：** JWT 或 Session 中包含租户 ID 后，是否就自动完成多租户隔离？

**考察点：** 身份边界、查询安全。

**参考答案：**

- 令牌中的租户声明只提供可信上下文来源之一，仍必须在后端每次查询和写入时应用租户范围。
- 不能信任请求 body、URL 或前端传来的租户 ID 来决定访问范围。
- Repository 或数据库访问层应有一致隔离策略，唯一约束也应包含租户维度。
- 后台任务、导出、缓存 key 和审计日志同样需要租户上下文。
- 对高隔离要求可考虑独立 schema 或数据库，但运维成本更高。

**深入追问：** 管理员跨租户查询应该如何设计？

**评分要点：** 使用显式高权限用例、审计和独立接口，不应通过“租户 ID 为空”绕过所有过滤。

## 六、PyQt 桌面开发

### 21. Qt 事件循环的作用是什么

**难度：** 初级至中级

**问题：** 为什么在按钮点击槽函数中执行长时间任务会让界面“未响应”？

**考察点：** GUI 线程、事件处理。

**参考答案：**

- Qt 主线程的事件循环负责处理输入、绘制、定时器、信号投递和窗口系统消息。
- 槽函数在 GUI 线程执行长时间计算或阻塞 I/O 时，事件循环无法继续处理绘制和输入，因此界面卡死。
- 长任务应移到工作线程、进程或异步任务，主线程只更新界面和处理轻量逻辑。
- 不能用频繁调用 `processEvents()` 作为常规解决方案，它可能造成重入和状态难以推理。

**深入追问：** 为什么窗口仍在计算，但操作系统显示“未响应”？

**评分要点：** 因为主线程长时间不处理窗口消息；任务是否仍在执行与 UI 是否响应是两件事。

### 22. 信号和槽解决了什么问题

**难度：** 初级至中级

**问题：** 信号槽与直接调用方法有什么区别？跨线程连接时需要注意什么？

**考察点：** 解耦、线程间通信。

**参考答案：**

- 信号表达事件发生，槽负责响应，可一对多连接并降低发送者对接收者的直接依赖。
- 同线程连接通常可直接调用；跨线程时通常通过队列投递，在接收对象所属线程的事件循环中执行。
- 发送的数据需要可安全传递，不能依赖即将失效的临时状态。
- 信号可能重复连接导致槽执行多次，连接和断开生命周期要清楚。
- 不应把所有业务都做成无方向的信号网络，否则数据流难以追踪。

**深入追问：** 一个槽被执行两次，如何判断是信号发射两次还是重复连接？

**评分要点：** 应检查连接建立位置、对象重建、日志和连接生命周期，而不是直接在槽里加防抖掩盖原因。

### 23. `QThread` 的正确使用方式是什么

**难度：** 中级

**问题：** 为什么常见推荐是创建 worker `QObject`，再使用 `moveToThread`，而不是把所有逻辑写进 `QThread` 子类？

**考察点：** 线程亲和性、职责分离。

**参考答案：**

- `QThread` 对象本身通常属于创建它的线程，它管理的是另一个线程的执行，不等于对象本身“住在”工作线程。
- 将 worker `QObject` 移到线程后，通过信号触发其槽，可让任务在工作线程事件循环中执行。
- 这样线程生命周期与业务任务职责分离，更便于取消、复用和测试。
- 继承 `QThread` 并重写 `run` 在纯计算或明确无事件循环需求时也可行，不能说绝对错误，但要理解差异。
- GUI 控件必须在主线程创建和更新，工作线程通过信号传递结果。

**深入追问：** 为什么直接从 worker 线程调用 `label.setText()` 有风险？

**评分要点：** Qt GUI 通常不是线程安全的，更新应投递到 GUI 线程。

### 24. 如何停止一个正在运行的 PyQt 后台任务

**难度：** 中级至高级

**问题：** 用户点击“取消”后，是否应该直接 `terminate()` 线程？

**考察点：** 协作式取消、资源一致性。

**参考答案：**

- 强制终止可能让锁、文件、数据库事务或 C++ 对象处于不一致状态，不应作为常规方案。
- 应使用取消标志、`requestInterruption()` 或任务队列，让 worker 在安全检查点主动退出。
- 阻塞 I/O 需要设置超时或使用可取消 API，否则线程无法及时响应取消。
- 退出时释放资源、发射完成状态，再执行 `thread.quit()`、`wait()` 和对象清理。
- UI 应区分“已请求取消”和“已取消完成”，避免立即允许冲突操作。

**深入追问：** 一个第三方库调用可能阻塞十分钟且不支持取消，怎么办？

**评分要点：** 可放入独立进程实现强隔离和终止，或通过超时与外部服务包装；线程无法安全强杀任意阻塞代码。

### 25. Qt 对象的父子关系和资源释放

**难度：** 中级

**问题：** Qt parent-child 机制如何影响对象生命周期？`deleteLater()` 有什么作用？

**考察点：** Python/C++ 双层对象、事件循环释放。

**参考答案：**

- Qt 父对象销毁时会销毁子对象，适当设置 parent 可减少手工释放。
- Python 包装对象的引用计数与底层 C++ 对象生命周期并不完全相同，可能出现 Python 引用仍在但 C++ 对象已删除的错误。
- `deleteLater()` 将删除安排到对象所属线程的事件循环中执行，适合避免在当前回调栈中立即销毁。
- 没有 parent 的长期对象需要保存 Python 引用，否则可能被垃圾回收；反之，全局引用和信号连接也可能造成对象无法释放。
- 线程对象、worker 和窗口关闭流程应明确谁拥有谁、何时断开和等待。

**深入追问：** 一个无 parent 的弹窗创建后立刻消失，可能是什么原因？

**评分要点：** 局部变量失去 Python 强引用后被回收；应由窗口或控制器持有，但不能无界保存。

### 26. Model/View 与直接操作表格控件如何选择

**难度：** 中级

**问题：** `QTableWidget` 和 `QTableView + QAbstractTableModel` 分别适合什么场景？

**考察点：** UI 数据模型、扩展性。

**参考答案：**

- `QTableWidget` 使用方便，适合数据量小、交互简单的工具界面。
- `QTableView` 配合模型将数据与展示分离，适合大数据、排序过滤、懒加载、复用和复杂编辑。
- 自定义模型需要正确实现行列数、数据角色、flags、编辑和变更通知。
- 数据变化时应使用合适的 `beginInsertRows`、`dataChanged`、reset 等通知，不能悄悄修改底层列表后期待界面自动刷新。
- 业务实体不应直接依赖控件，可以由模型适配领域数据。

**深入追问：** 十万行数据是否应该一次性全部创建 `QTableWidgetItem`？

**评分要点：** 通常不应；可使用 Model/View、分页、虚拟化或按需获取，减少对象和绘制成本。

### 27. PyQt 界面状态如何组织

**难度：** 中级至高级

**问题：** 一个窗口同时负责 API 请求、数据库、校验、业务计算和控件更新，会出现什么问题？

**考察点：** 模块职责、状态流。

**参考答案：**

- UI 类会迅速膨胀，业务规则难以测试，异步回调互相修改控件造成状态混乱。
- 应将业务用例、数据访问、任务执行和展示模型分离，窗口负责用户事件与呈现。
- 可采用 Presenter、ViewModel、Controller 或简化的单向状态更新方式，具体模式不是目的。
- 关键是明确唯一事实来源、任务状态机和从后台结果到 UI 的单向数据流。
- 不要把全局单例当作跨窗口共享状态的默认方案。

**深入追问：** 用户快速切换两条记录，较早请求后返回并覆盖当前界面，如何解决？

**评分要点：** 使用请求版本、选择 ID 校验、取消旧任务或状态归属判断，拒绝过期结果写入当前视图。

### 28. PyQt 中定时器和轮询如何使用

**难度：** 中级

**问题：** `QTimer` 是否会为每次回调创建新线程？高频定时器有哪些风险？

**考察点：** 事件循环、定时任务。

**参考答案：**

- `QTimer` 的 timeout 通常由其所属线程的事件循环触发，不会自动创建新线程。
- 如果回调耗时超过间隔，事件处理会延迟，不能依靠高频定时器获得硬实时能力。
- 高频刷新会增加 CPU 和重绘压力，应合并更新、限制频率或由数据变化触发。
- 定时器的线程亲和性必须正确，启动和停止通常应在所属线程进行。
- 网络轮询还需考虑超时、并发重叠、退避和窗口关闭后的停止。

**深入追问：** 上一次请求尚未结束，下一次定时器又触发，如何避免并发堆积？

**评分要点：** 使用运行中状态、单次定时器在完成后重启、取消或请求合并，并处理异常后恢复。

### 29. PyQt 网络访问应如何实现

**难度：** 中级

**问题：** 桌面程序调用 HTTP API，可以使用 `requests` 吗？

**考察点：** 阻塞调用、Qt 网络栈和线程。

**参考答案：**

- 可以使用 `requests`，但不能在 GUI 线程中执行长时间同步请求，应放到工作线程并设置连接与读取超时。
- 也可以使用 Qt 的 `QNetworkAccessManager`，通过事件驱动信号处理响应，更自然地集成 Qt 事件循环。
- 无论选择哪种方式，都要处理取消、重试、代理、TLS、证书、认证过期和窗口关闭时的任务清理。
- 网络回调不能直接假设当前页面仍存在或仍选择原记录。
- 下载大文件应流式写入，提供进度并验证完整性。

**深入追问：** 是否应该对所有网络错误自动重试三次？

**评分要点：** 只对幂等且可能瞬时恢复的失败按退避策略重试；认证、参数错误和非幂等请求不能盲目重试。

### 30. PyQt 打包发布有哪些常见问题

**难度：** 中级至高级

**问题：** 使用 PyInstaller 等工具后，为什么开发环境正常，用户电脑上却启动失败？

**考察点：** 依赖收集、运行环境、可诊断性。

**参考答案：**

- 动态导入、Qt 插件、平台 DLL、资源文件、字体和本地扩展可能未被正确收集。
- one-file 模式需要临时解压，启动较慢，也可能受杀毒软件或权限策略影响。
- 应在干净的目标系统或虚拟机中测试，与构建机隔离，并覆盖不同架构和系统版本。
- 文件路径不能依赖源码目录，应区分打包资源、用户配置、缓存和日志目录。
- 发布包应有版本信息、签名、崩溃日志和诊断入口，不能只在开发机双击验证。

**深入追问：** 用户只反馈“打不开”，你希望程序提供哪些诊断信息？

**评分要点：** 启动日志、版本、系统环境、异常堆栈、依赖加载错误、崩溃转储或安全的诊断包。

### 31. 桌面应用自动更新如何设计

**难度：** 高级

**问题：** 设计一个 Windows 桌面应用的安全更新机制。

**考察点：** 发布状态机、安全与回滚。

**参考答案：**

- 应用检查受信任更新源，获取版本、变更和包信息，不应仅凭可修改的版本字符串下载执行。
- 更新包应通过 TLS 下载并校验哈希和数字签名，防止篡改。
- 主程序运行时通常不能直接覆盖自身文件，可由独立 updater 在程序退出后替换。
- 更新过程应支持下载、校验、等待退出、备份、替换、启动验证和失败回滚状态。
- 用户数据和程序文件分离，数据库或配置迁移要兼容旧版本并有恢复策略。
- 支持灰度、强制更新策略和错误上报，但不能让失败更新导致应用永久无法启动。

**深入追问：** 新版本启动即崩溃，如何自动回退？

**评分要点：** 保留旧版本，使用启动成功确认或健康标记；超过时间未确认则由 updater 恢复。

### 32. PyQt 与 `asyncio` 如何协作

**难度：** 高级

**问题：** Qt 和 `asyncio` 都有事件循环，直接同时运行会有什么问题？

**考察点：** 多事件循环集成。

**参考答案：**

- 两个事件循环都希望控制当前线程，直接分别 `run_forever` 会互相阻塞。
- 可以使用专门的事件循环适配库将 asyncio 调度集成 Qt，或把异步逻辑放在独立线程中并通过信号通信。
- 需要明确任务创建、异常收集、取消和应用关闭流程。
- 选择集成方案前应确认第三方库是否真正需要 asyncio；简单 HTTP 请求可能使用 Qt 网络栈更直接。
- 不能在 GUI 回调中随意调用 `asyncio.run`，它会创建并阻塞运行新的事件循环。

**深入追问：** 窗口关闭时仍有 asyncio task，如何处理？

**评分要点：** 停止接收新任务、取消并等待任务清理，关闭客户端会话，再结束集成事件循环。

## 七、数据库、缓存与系统设计

### 33. ORM 的 N+1 查询是什么

**难度：** 中级

**问题：** 查询 100 个订单后逐个访问客户信息，为什么可能产生 101 次 SQL？

**考察点：** ORM 加载策略、性能证据。

**参考答案：**

- 主查询获取订单，随后每个订单的延迟加载关系各执行一次查询，形成 N+1。
- 可根据用例使用 join eager loading、select-in loading、预取或专门查询 DTO。
- 不能无差别 eager load 所有关联，否则可能产生笛卡尔膨胀和大量无用数据。
- 应通过 SQL 日志、trace 和查询计数验证，而不是只凭页面慢猜测。
- 序列化阶段访问懒加载属性尤其容易隐藏查询。

**深入追问：** 为什么关闭数据库会话后访问懒加载关系会失败？

**评分要点：** ORM 需要活跃会话发起查询；应在明确事务/查询边界内加载所需数据。

### 34. 如何保证库存或余额更新正确

**难度：** 中级

**问题：** Python 中使用一个全局 `Lock` 是否足以保证多实例服务的库存安全？

**考察点：** 进程边界、数据库并发控制。

**参考答案：**

- 进程内锁只约束当前进程线程，无法协调其他 worker、进程或服务器。
- 可使用数据库条件更新、悲观锁、乐观版本号和事务约束保证事实存储正确性。
- 唯一约束和检查约束是重要最终防线。
- 分布式锁可以协调，但仍有租约和故障问题，不应替代数据库不变量。
- 还要处理幂等、事务重试和外部调用结果不确定。

**深入追问：** SQLite、本地桌面单机和多实例 Web 服务的锁策略是否相同？

**评分要点：** 应根据部署拓扑、数据库并发模型和写入规模分别设计，不能只看语言。

### 35. 如何设计幂等的任务提交接口

**难度：** 中级至高级

**问题：** 用户在桌面端多次点击“开始导入”，网络超时后又重试，后端如何防止重复任务？

**考察点：** 跨端重试、任务状态。

**参考答案：**

- 客户端针对同一次用户操作生成稳定幂等键，按钮防抖只是体验优化，不是最终保障。
- 后端使用调用方加幂等键的唯一约束，保存请求参数摘要、任务 ID 和状态。
- 重复请求参数一致时返回同一任务；参数不一致时拒绝复用。
- 状态至少区分已接收、运行中、成功、失败和取消，客户端可查询或订阅进度。
- worker 自身也要防止重复消费产生重复副作用。

**深入追问：** 用户确实想用同一文件重新导入一次，怎么办？

**评分要点：** 新的用户操作生成新幂等键；业务去重与请求幂等应分开建模。

### 36. 设计一个大文件导入系统

**难度：** 高级

**问题：** 桌面端上传几十万行数据到 Python 后端，要求展示进度和错误报告，请给出设计。

**考察点：** 流式处理、异步任务、状态机。

**参考答案：**

- 桌面端分块或流式上传，显示上传进度，支持超时与可恢复策略；服务端限制大小、类型并安全存储。
- 上传完成后创建后台任务，worker 流式解析或分批读取，避免整个文件进入内存。
- 校验分为格式、字段和业务关联；错误记录写入单独报告，不应全部塞进任务状态字段。
- 明确导入语义是全量原子、按批提交还是合法行成功，不同语义决定事务和恢复方式。
- 进度可以通过轮询、SSE 或 WebSocket 获取，需要限频并处理重连。
- 还要考虑公式注入、恶意压缩包、编码、重复导入、取消、重试和审计。

**深入追问：** 进度显示 90% 后任务失败，用户能否直接继续？

**评分要点：** 取决于检查点和提交语义；应设计可恢复批次或明确重新开始与回滚策略。

### 37. 线上 API P99 突然升高如何排查

**难度：** 高级

**问题：** 平均延迟正常，但少量用户请求超过 10 秒，你会如何定位？

**考察点：** 可观测性、长尾故障。

**参考答案：**

1. 确认慢请求时间、实例、参数、租户、数据量和最近发布。
2. 使用 trace 分解应用、数据库、缓存、下游和队列等待。
3. 检查同步调用是否阻塞事件循环、线程池是否排队、数据库池是否耗尽。
4. 对比慢请求 SQL 执行计划、锁等待、重试、DNS 和网络连接建立时间。
5. 检查 GC、CPU、RSS、磁盘和容器限额，并根据证据止损。
6. 修复后通过回放、压测或灰度验证，并补充高分位告警。

**深入追问：** 为什么只增加 Uvicorn worker 可能让问题更严重？

**评分要点：** 更多 worker 会增加数据库连接、内存和下游并发，可能放大真正瓶颈。

### 38. Python 项目如何进行模块化

**难度：** 高级

**问题：** 一个项目按 `routers`、`services`、`models`、`utils` 组织，增长后为什么仍可能难维护？

**考察点：** 业务边界、依赖方向。

**参考答案：**

- 仅按技术层划分会让一个业务功能散落在全项目，`services.py` 和 `utils.py` 容易成为无边界的大文件。
- 可先按业务能力拆模块，在模块内部区分接口、用例、领域规则和基础设施适配。
- 路由负责协议转换，应用服务编排用例，核心规则应尽量保持纯函数或明确状态对象，数据访问通过接口隔离。
- 模块之间使用明确契约，避免直接导入内部 ORM 模型并修改对方数据。
- Python 的动态导入便利也容易造成循环依赖，需要通过依赖方向和组合入口治理。

**深入追问：** 什么时候纯函数特别适合承载业务规则？

**评分要点：** 输入输出明确、无需 I/O、规则可组合且需要大量边界测试时，纯函数能降低隐藏状态和测试成本。

## 八、前端与跨端协作能力

### 39. 浏览器请求与桌面 HTTP 请求有什么不同

**难度：** 中级

**问题：** 为什么浏览器前端会遇到 CORS，而 PyQt 桌面程序使用 HTTP 客户端通常不会？

**考察点：** 浏览器安全模型、客户端差异。

**参考答案：**

- CORS 是浏览器同源策略的一部分，由浏览器决定是否允许页面脚本读取跨源响应。
- 普通桌面 HTTP 客户端不处于浏览器页面沙箱，通常不执行 CORS 限制。
- 这不代表桌面客户端更“可信”；用户可以修改客户端请求，后端仍必须认证、授权和校验。
- 浏览器 Cookie、CSRF、预检与桌面端令牌存储的风险模型不同。
- 后端安全不能依赖请求来自官方前端或桌面程序。

**深入追问：** 桌面程序把长期 Token 明文保存到配置文件有什么风险？

**评分要点：** 本机其他用户或恶意软件可读取；可使用系统凭据存储、短期令牌、刷新策略和设备撤销机制。

### 40. React/Vue 中如何管理接口状态

**难度：** 中级

**问题：** 是否应该把所有后端响应都复制进全局 store？

**考察点：** 服务端状态、数据一致性。

**参考答案：**

- 服务端状态带有缓存、过期、重试、失效和并发请求语义，可交给专门的数据请求库管理。
- 组件交互状态放在最近范围，真正跨页面共享的客户端状态再进入全局 store。
- 重复保存接口结果会形成多个事实来源，更新后容易不一致。
- 提交变更后可根据业务使用失效重查、乐观更新或精准修改缓存，并处理失败回滚。
- 列表筛选、分页和排序应体现在查询 key 或请求参数中。

**深入追问：** 用户连续搜索，旧请求比新请求更晚返回，如何避免结果倒退？

**评分要点：** 取消旧请求、使用请求序号或由查询库按 key 管理，只让当前查询结果更新界面。

### 41. TypeScript 类型能否替代运行时校验

**难度：** 中级

**问题：** 后端生成 OpenAPI 类型后，前端是否可以完全相信响应结构？

**考察点：** 静态与运行时边界。

**参考答案：**

- TypeScript 类型在编译后被擦除，不能自动验证网络 JSON。
- 生成类型可减少契约重复，但部署版本错位、代理错误页和第三方数据仍可能不符合类型。
- 对关键外部边界可做运行时 schema 校验，并提供可观测的降级错误。
- 日期、时区、大整数、Decimal、枚举和 `null` 需要在 Python 与 JavaScript 之间明确编码方式。
- `as SomeType` 只是断言，不是校验。

**深入追问：** Python `Decimal` 金额为什么不宜直接转成 JavaScript 浮点数计算？

**评分要点：** 二进制浮点会产生精度问题；可用字符串、最小货币单位整数或前端 decimal 库并统一舍入规则。

## 九、AI 编程工具使用能力

### 42. 如何使用 AI 完成 Python 或 PyQt 功能

**难度：** 初级至中级

**问题：** 请用一个真实案例说明从需求到提交的全过程。

**考察点：** 上下文、拆解和验证。

**参考答案：**

- 先定义需求、非目标、输入输出、线程或事件循环约束和验收条件。
- 让工具读取相关模块和依赖版本，先提出小范围方案，再实施可审查的改动。
- 对 PyQt 重点检查 GUI 线程、对象生命周期、信号重复连接和关闭流程；对 Web 重点检查事务、异步阻塞和权限。
- 运行单元测试、类型检查、格式检查及真实界面或 API 测试，观察日志和资源释放。
- 审查最终 diff，删除无关改动，并确保自己能够解释每个关键选择。

**深入追问：** 要求候选人说明一次 AI 生成代码能运行但设计错误的案例。

**评分要点：** 真实使用者应能提供具体错误、发现证据和修正过程，而非只说“效率提高”。

### 43. 如何验证 AI 生成的 Python API

**难度：** 中级

**问题：** AI 建议使用某个库的方法，但项目运行时报属性不存在，你如何处理？

**考察点：** 版本核验、事实来源。

**参考答案：**

- 检查当前虚拟环境实际安装版本和依赖声明。
- 查看官方文档、函数签名、变更记录或包源码，确认 API 是否存在以及适用版本。
- 编写最小复现或在隔离环境验证，不继续要求 AI 反复猜方法名。
- 评估升级依赖是否影响其他模块和打包环境，不为一个 API 盲目升级整个项目。
- 把最终方案和版本约束写回项目配置与测试。

**深入追问：** 为什么 PyQt5、PyQt6、PySide6 的示例不能总是直接混用？

**评分要点：** 枚举、模块路径、信号 API、许可证和绑定行为存在差异，必须按实际依赖核验。

### 44. AI 生成测试的价值和局限

**难度：** 中级

**问题：** AI 一次生成了很多测试且全部通过，是否说明功能可靠？

**考察点：** 测试质量、错误预言机。

**参考答案：**

- AI 擅长补充边界组合和测试骨架，但可能只重复实现逻辑，导致“代码错、测试也按同样方式错”。
- 需要从业务不变量和独立预期出发设计断言，而不是只追求覆盖率。
- Mock 过多可能绕过数据库事务、Qt 事件循环、线程和真实序列化问题。
- 对 PyQt 可测试纯业务逻辑、模型状态和信号结果，并保留少量真实 UI 流程测试。
- 对并发和异步代码要验证超时、取消、重复和资源清理，不能只测成功路径。

**深入追问：** 如何判断一个测试是在验证行为还是复述实现？

**评分要点：** 修改内部实现但保持外部行为时，合理测试应继续通过；断言应基于契约和不变量。

### 45. 如何安全地向 AI 提供项目上下文

**难度：** 中级

**问题：** 哪些内容不应直接上传给外部 AI 服务？

**考察点：** 隐私、凭据和代码治理。

**参考答案：**

- 不上传真实密钥、Token、客户隐私、生产数据库、未脱敏日志和受限制源码。
- 只提供完成任务所需的最小文件和最小数据，对路径、账号、订单和设备信息脱敏。
- 使用组织批准的工具并了解数据保留政策；敏感项目考虑企业配置、私有模型或离线方案。
- 检查 AI 新增依赖的许可证、维护状态和供应链风险。
- 如果秘密可能已经暴露，应立即轮换，并检查使用记录，而不是只删除对话。

**深入追问：** 桌面应用崩溃日志中可能包含哪些敏感数据？

**评分要点：** 文件路径、用户名、Token、请求参数、文档内容和本机环境都可能敏感，需要采集前脱敏和授权。

### 46. AI 应如何参与代码评审和重构

**难度：** 高级

**问题：** 如何让 AI 帮助重构一个 2000 行的 PyQt 主窗口，而不造成大规模不可控修改？

**考察点：** 渐进式重构、模块边界。

**参考答案：**

- 先用测试、日志或人工流程固定关键行为，识别窗口中的业务规则、I/O、任务状态和展示职责。
- 让 AI 先绘制依赖和数据流，选择一个窄切片提取，例如纯计算、API client 或任务状态模型。
- 每次只移动一个职责，保持可运行，比较 diff 并执行相关测试和界面验证。
- 不应直接让 AI“重写整个窗口”，否则容易丢失隐藏行为、信号连接和对象生命周期约束。
- 最终目标是清晰的单向数据流和模块边界，而不是文件行数平均分配。

**深入追问：** 第一个最适合提取的部分如何选择？

**评分要点：** 优先选择依赖少、输入输出明确、可测试且业务价值高的逻辑，而非先拆最复杂的线程代码。

## 十、爬虫与数据采集

本节用于考察候选人是否能构建稳定、可维护、合规的数据采集系统。面试时应要求候选人明确目标站点、数据授权、访问频率、数据用途和停止条件。不要把“能绕过限制”作为爬虫能力的评价标准。

### 47. 一个 Python 爬虫请求需要关注哪些 HTTP 细节

**难度：** 初级至中级

**问题：** 使用 `requests`、`httpx` 或类似库请求页面时，需要关注哪些请求和响应信息？

**考察点：** HTTP 基础、会话管理、错误判断。

**参考答案：**

- 请求方法、URL 编码、查询参数、请求体、超时、代理、TLS 和连接复用。
- 状态码、重定向、响应编码、`Content-Type`、压缩、缓存头和响应大小。
- Cookie、会话、认证信息和 CSRF 等状态必须按照授权系统的正常流程处理，不能硬编码真实凭据。
- 不能只判断 HTTP 200；站点可能用 200 返回登录页、错误页或限流提示，需要校验内容和业务字段。
- 应设置连接和读取超时，记录请求 ID、耗时和安全的错误摘要。

**深入追问：** 为什么网页浏览器能看到数据，但程序拿到的响应却是登录页？

**评分要点：** 应考虑会话 Cookie、认证流程、请求方法、重定向、必要请求头和页面实际数据来源；不能直接归因于“加 User-Agent”。

### 48. 如何判断页面数据是服务端渲染还是 JavaScript 动态加载

**难度：** 中级

**问题：** 爬虫打开 HTML 后找不到浏览器中显示的列表，你会如何定位数据来源？

**考察点：** 页面渲染模型、网络分析。

**参考答案：**

1. 对比原始 HTML 与渲染后的 DOM，确认数据是否由脚本插入。
2. 在授权和低频测试环境中观察浏览器开发者工具的 Fetch/XHR 请求，定位数据接口、参数、分页和响应结构。
3. 确认接口是否需要登录状态、CSRF、特定上下文或一次性请求标识。
4. 若接口是稳定且被允许使用的公开接口，优先直接调用并进行契约测试；否则使用 Playwright 等浏览器自动化完成正常页面流程。
5. 不应只复制浏览器里的临时令牌，也不应把浏览器自动化作为绕过访问控制的工具。

**深入追问：** 什么时候应该使用浏览器自动化，而不是直接请求接口？

**评分要点：** 当数据只能在浏览器执行后生成、需要真实交互或必须复现用户授权流程时使用；否则直接 HTTP 通常更轻量、稳定、易部署。

### 49. 爬虫如何处理限速、重试和访问礼仪

**难度：** 中级

**问题：** 设计一个不会给目标站点造成异常压力的采集器，需要哪些机制？

**考察点：** 稳定性、合规和资源治理。

**参考答案：**

- 先确认目标站点授权、服务条款、公开范围、`robots.txt` 约束和数据使用边界。
- 设置全局和站点级并发上限、请求间隔、连接池上限和带随机抖动的退避策略。
- 只对网络抖动、明确的服务端临时错误等可恢复失败重试；参数错误、权限失败和明确拒绝不应反复重试。
- 识别 429、503、验证码页面和限流响应，进入暂停或人工确认状态，而不是持续加大并发。
- 使用缓存、增量采集、条件请求和断点续采，减少重复访问。
- 提供停止开关、预算上限、请求审计和异常告警。

**深入追问：** 为什么“代理池越大越好”不是合理的工程答案？

**评分要点：** 代理不能替代授权和限速；会增加复杂度、合规风险、数据一致性问题和故障定位成本。

### 50. 如何设计稳定的网页解析和数据质量校验

**难度：** 中级

**问题：** 页面结构经常变化，如何避免解析器悄悄产生大量错误数据？

**考察点：** 解析鲁棒性、数据质量、可观测性。

**参考答案：**

- 将抓取、解析、标准化、校验和存储拆成明确阶段，避免一个函数完成全部工作。
- 优先依赖稳定语义字段或公开结构化数据，CSS 选择器和 XPath 需要集中管理并配套样例测试。
- 对关键字段做类型、范围、必填、唯一性和关联一致性校验，记录缺失率和异常比例。
- 解析失败时保存经脱敏的原始响应或版本化样本，便于复现；不应无限保存敏感内容。
- 通过 schema 版本、质量阈值和告警阻止“解析成功但字段全部为空”的结果进入主库。
- 站点变更时优先暂停该来源或进入隔离区，不能用默认值掩盖未知结构。

**深入追问：** 解析器没有抛异常，但入库数量突然增加十倍，你如何发现？

**评分要点：** 应建立数量、字段缺失率、重复率、数值分布和来源级质量监控，而不是只监控程序异常。

### 51. 如何设计可恢复的分布式爬虫

**难度：** 高级

**问题：** 需要采集多个来源、百万级 URL，并支持暂停、重试和断点续采，你会如何分层？

**考察点：** 任务调度、状态机、幂等和容量治理。

**参考答案：**

- URL 发现、调度队列、抓取 worker、解析标准化、去重存储和质量监控分开设计。
- URL 任务至少区分待处理、处理中、成功、可重试失败、永久失败和暂停；需要租约或可回收机制处理 worker 崩溃。
- 使用规范化 URL 和去重键，结果写入使用幂等约束；不能只依赖内存集合去重。
- 不同来源设置独立并发、限速和失败预算，防止一个来源拖垮全部任务。
- 任务与原始快照、解析版本和结果版本关联，支持重新解析而不必重复请求来源。
- 监控队列堆积、成功率、延迟、重试率、来源质量和资源成本。

**深入追问：** worker 抓取成功但在更新任务状态前崩溃，会怎样？

**评分要点：** 可能被重新投递，因此结果存储和副作用必须幂等；任务租约过期后允许回收，不能假设恰好执行一次。

### 52. 爬虫中的去重、增量采集和数据版本如何处理

**难度：** 高级

**问题：** 同一内容有多个 URL，页面会更新，业务又需要知道历史变化，如何建模？

**考察点：** 数据身份、内容版本和存储设计。

**参考答案：**

- URL 规范化只能解决一部分重复，还要基于来源标识、业务主键、规范化内容或稳定指纹判断实体身份。
- 使用 `ETag`、`Last-Modified`、更新时间或内容摘要做增量判断，但不能盲信页面时间字段。
- 将当前视图和历史版本分开保存，记录采集时间、解析器版本、来源和质量状态。
- 内容指纹用于发现变化，不应直接当作业务唯一 ID，需评估字段顺序、动态时间和广告内容造成的误判。
- 增量任务需要处理删除、下架、权限变化和长期未访问数据。

**深入追问：** 页面每次响应都包含动态时间，如何避免每次都被判断为内容变化？

**评分要点：** 应先做字段级规范化、剔除已知非业务字段，并通过样本验证规则，不应简单对整个 HTML 做哈希。

### 53. 如何测试和发布一个爬虫

**难度：** 中级

**问题：** 爬虫依赖外部页面，如何让测试稳定且不频繁请求真实站点？

**考察点：** 测试隔离、可复现性。

**参考答案：**

- 将 HTTP 客户端、解析器、业务标准化和存储接口分离。
- 保存经授权和脱敏的 HTML/JSON 样本，在离线测试中验证解析和字段校验。
- 使用 HTTP mock 或本地测试服务器验证超时、重定向、限流、编码错误和异常响应。
- 对解析器做回归测试，样本按页面版本管理；对调度器测试重试、租约、取消和幂等。
- 发布前进行小范围灰度，设置自动暂停阈值和回滚配置。

**深入追问：** 只测试选择器命中数量是否足够？

**评分要点：** 不足；还要验证字段语义、类型、关联关系、空值比例、重复和异常分布。

## 十一、逆向分析与协议理解

本节只适用于获得授权的软件、内部系统、公开样本、互操作性研究、故障排查和安全测试。面试中应重点考察分析方法、证据链和边界意识，不考察绕过授权、破解付费功能、提取他人凭据或规避安全控制的能力。

### 54. 授权的逆向分析通常从哪里开始

**难度：** 初级至中级

**问题：** 拿到一个自己有权分析的 Python 程序或桌面客户端，你会如何建立分析计划？

**考察点：** 范围控制、证据记录、分析流程。

**参考答案：**

1. 确认授权范围、目标问题、可使用的样本和禁止操作，保留原始文件只读副本。
2. 记录文件哈希、版本、运行环境、依赖、启动参数和可观察行为。
3. 先做静态检查：文件类型、目录结构、字符串、导入和资源；再做动态观察：文件、进程、日志和授权的网络请求。
4. 将观察结果与源码、文档或已知版本交叉验证，形成可复现的最小结论。
5. 派生产物与原始产物分开保存，避免修改样本后失去证据来源。

**深入追问：** 为什么不能一上来就修改程序或注入大量脚本？

**评分要点：** 会破坏基线、引入新行为并降低证据可信度；应先被动观察，再逐步改变一个变量。

### 55. Python 打包程序有哪些静态分析线索

**难度：** 中级

**问题：** 对授权的 PyInstaller 或类似打包产物，你会查看哪些内容？

**考察点：** Python 打包结构、依赖识别。

**参考答案：**

- 识别文件类型、启动入口、归档结构、Python 运行时和第三方扩展。
- 查看模块名、导入关系、字符串、资源、版本信息和配置模板，注意区分代码、测试数据和诱饵内容。
- 对字节码或可读资源做版本匹配和静态审查，不把反编译结果当作原始源码。
- 关注动态导入、插件发现、环境变量和外部配置，因为它们可能决定运行时行为。
- 对 native 扩展需要单独按平台和 ABI 分析，避免仅凭 Python 文件得出完整结论。

**深入追问：** 为什么反编译出的 Python 代码可能与原始代码不同？

**评分要点：** 编译优化、版本差异、动态生成、丢失注释和名称信息都会造成差异，结论需要运行时证据验证。

### 56. 如何分析一个客户端的网络协议行为

**难度：** 中级至高级

**问题：** 在已获授权的测试环境中，如何确认桌面客户端登录、查询和提交操作对应的请求链路？

**考察点：** 网络证据、状态机、协议理解。

**参考答案：**

- 在隔离测试账号和测试数据下记录操作时间线、请求方法、URL、状态码、请求/响应结构和前后状态变化。
- 一次只执行一个动作，清理或标记会话状态，区分启动请求、心跳、配置请求和业务请求。
- 关联 UI 操作、日志和网络请求，确认参数来源、分页、错误码和重试语义。
- 对 HTTPS 只在有权控制的测试环境中使用正规调试代理或服务端日志，不触碰第三方用户流量或私钥。
- 记录脱敏后的协议样本，使用最小重放验证假设；不把重放用于绕过认证或扩大访问范围。

**深入追问：** 客户端请求返回超时，能否直接判定服务端没有执行？

**评分要点：** 不能；需要服务端 trace、幂等键、任务查询或审计记录判断结果。

### 57. 静态分析和动态分析应如何配合

**难度：** 中级

**问题：** 静态代码看不出配置来源，但运行时行为又依赖环境变量，你会如何继续？

**考察点：** 多证据关联、运行时验证。

**参考答案：**

- 静态分析用于建立候选路径、调用关系和可能的配置读取点，动态分析用于确认实际执行分支。
- 在隔离环境中逐项改变一个配置变量，观察日志、文件、请求和返回状态的变化。
- 使用断点、函数调用日志、系统级观测或测试替身定位配置从读取到使用的链路。
- 对动态导入、反射和生成代码保持谨慎，不能仅凭搜索不到字符串就认为不存在。
- 所有实验都应可重复，记录环境、输入、输出和清理步骤。

**深入追问：** 运行时行为与源码不一致时，优先检查哪些原因？

**评分要点：** 检查执行产物版本、启动路径、缓存、插件、环境变量、配置覆盖和是否分析了错误进程。

### 58. 如何识别“加密”“编码”和“混淆”

**难度：** 中级

**问题：** 看到一段 Base64、压缩数据或自定义字符串变换，如何避免错误判断？

**考察点：** 数据变换、密码学基本概念。

**参考答案：**

- 编码主要解决表示和传输，不提供保密性；Base64 可以直接逆向还原。
- 压缩改变数据表示并减少体积，也不等同于加密。
- 混淆提高阅读成本，通常不提供严格的机密性保证。
- 真正的加密需要算法、密钥、随机数、模式、完整性校验和密钥管理；不能只看字符串是否不可读。
- 分析时应从输入输出、长度、熵、固定头、错误行为和密钥来源建立可验证假设，不应把未知变换直接命名为“加密”。

**深入追问：** 为什么“有一个密钥变量”仍不能证明使用了安全加密？

**评分要点：** 可能是常量、弱密钥、编码参数或自定义异或；需要确认算法、密钥管理、随机性和完整性。

### 59. 授权动态调试中如何控制风险

**难度：** 高级

**问题：** 需要定位客户端某个功能的崩溃或错误请求，如何进行动态调试而不污染环境？

**考察点：** 调试安全、最小实验、可复现性。

**参考答案：**

- 使用隔离虚拟机、测试账号、非生产数据和可回滚快照，限制网络和文件权限。
- 先用日志、崩溃转储、调用栈和资源监控缩小范围，再设置窄范围断点或观测点。
- 一次只改变一个输入或配置，保留原始运行记录和修改记录。
- 处理敏感数据时脱敏；不执行来历不明的脚本，不把调试能力扩展到无关进程或用户数据。
- 结束后清理测试凭据、临时文件和代理配置，输出可复现的修复验证结果。

**深入追问：** 为什么“为了方便，直接在生产客户端上挂调试器”是不合格方案？

**评分要点：** 可能泄露敏感数据、改变时序、影响用户和破坏证据；应优先复制问题到隔离环境。

### 60. 逆向分析成果如何转化为工程改进

**难度：** 高级

**问题：** 通过授权分析发现客户端和服务端协议存在重复提交风险，你会如何推动修复？

**考察点：** 从分析到修复、跨团队协作。

**参考答案：**

- 用脱敏请求样本、时间线、服务端日志和最小复现证明风险，不公开真实凭据或用户数据。
- 先明确业务影响和可利用前提，再提出服务端幂等键、唯一约束、状态机和审计方案。
- 客户端增加请求状态管理、超时后的查询和有限重试，但不把正确性只放在客户端。
- 增加协议契约测试、并发测试、故障注入和监控，验证修复覆盖重复、超时和部分失败。
- 按组织流程报告并跟踪修复，不在未授权范围内继续扩大测试。

**深入追问：** 为什么只在客户端禁用提交按钮不能解决问题？

**评分要点：** 客户端可被重复调用、崩溃或网络重试绕过；服务端必须实现最终幂等和状态约束。

## 十二、项目经历核验题

### 61. 说明一个 Python 项目的端到端请求链路

**难度：** 全级别

**深入追问：** 让候选人画出一次写操作的数据变化和事务边界。

### 62. 说明一个最困难的 PyQt 问题

**难度：** 中级至高级

**问题：** 请描述一次界面卡顿、随机崩溃、线程退出失败、内存增长或打包失败的问题。

**考察点：** 桌面开发真实性、排障证据。

**参考答案判断：**

**深入追问：** 修复后如何证明不是偶然不再出现？

**评分要点：** 应有稳定复现、压力或长时间测试、资源指标和回归测试。

### 63. 描述一次线上或客户端故障复盘

**考察点：** 排障过程、责任和复盘。

**参考答案判断：**

- 能坦诚说明个人判断错误并纠正，通常比完美故事更可信。

**深入追问：** 如果只能补一个监控或诊断能力，会选择什么？

**评分要点：** 选择应直接覆盖本次最早无法确认的环节。

## 十三、现场编码与设计题

### 64. 编码题：实现可取消的批处理任务

**难度：** 中级

**题目：** 实现一个处理大量记录的任务，支持进度上报、取消、错误收集和最终状态。可使用 Python 代码或伪代码；桌面候选人需说明如何接入 PyQt。

**最低要求：**

- 不一次性加载全部数据。
- 有明确的待运行、运行中、成功、失败、取消状态。
- 在安全检查点响应取消，使用 `finally` 释放资源。
- 错误不会无限积累在内存中。
- PyQt 中不从工作线程直接操作控件。

**优秀表现：**

- 将纯处理逻辑与线程/Qt 适配分开。
- 控制进度更新频率，避免高频信号拖慢 UI。
- 定义部分成功和重试语义。
- 有可测试的取消、异常和资源释放方案。

### 65. 编码题：实现接口幂等记录

**难度：** 中级至高级

**题目：** 给定用户 ID、幂等键和任务参数，实现“相同操作只创建一个任务”的核心流程。

**最低要求：**

- 使用数据库唯一约束，而不是仅在 Python 中先查后插。
- 保存请求参数摘要和任务 ID。
- 重复且参数一致时返回原任务。
- 相同键但参数不一致时返回冲突。
- 正确处理并发插入异常和事务回滚。

**优秀表现：** 定义处理中、成功、失败和过期策略，并说明客户端超时后的查询与重试流程。

### 66. 设计题：离线可用的 PyQt 业务客户端

**难度：** 高级

**题目：** 设计一个可在断网时录入数据、联网后同步到服务端的 PyQt 客户端。

**候选人需要说明：**

1. 本地数据库、服务端数据库和 UI 状态的职责。
2. 本地操作日志或同步队列的数据结构。
3. 临时 ID 与服务端 ID 的映射。
4. 幂等上传、拉取游标和删除语义。
5. 同一记录在两端修改时的冲突策略。
6. 网络恢复、重试、失败提示和人工处理。
7. 凭据、本地敏感数据加密和设备撤销。
8. 数据库迁移、应用升级和回滚。

**优秀表现：** 先定义业务允许的冲突语义，再设计同步协议；不会简单用“以最后更新时间覆盖”处理所有数据，也不会让 UI 直接同时写本地库和远端 API 而缺少状态机。
