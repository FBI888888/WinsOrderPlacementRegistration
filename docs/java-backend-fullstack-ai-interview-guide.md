# Java 后端、前端与 AI 编程能力面试题库

## 一、使用说明

本文供面试官按候选人经历自由抽题，不建议逐题询问。

难度标记：

- **初级**：验证基础概念是否准确，能否完成明确的小型任务。
- **中级**：验证实际开发、排障和技术取舍能力。
- **高级**：验证架构设计、复杂故障治理和团队工程能力。

建议一次面试选题方式：

1. Java 基础与 JVM：3 至 5 题。
2. 并发编程：2 至 4 题。
3. Spring 与 Web：3 至 5 题。
4. 数据库、缓存和分布式：3 至 5 题。
5. 工程实践与系统设计：2 至 4 题。
6. 前端能力：2 至 3 题。
7. AI 编程工具：2 至 3 题。
8. 项目核验、编码或设计题：至少 1 项。

开放题不要求候选人与参考答案逐字一致。重点判断其是否能说明原理、适用边界、风险和验证方式。

## 二、通用评分尺度

每道题可按 0 至 4 分记录：

- **0 分**：不了解，或回答与事实明显冲突。
- **1 分**：记得术语，但无法解释原理和实际用法。
- **2 分**：基础正确，能完成常规开发，但缺少边界意识。
- **3 分**：能结合项目解释取舍、风险、排障和验证方法。
- **4 分**：能从系统、团队和长期维护角度提出完整方案，并识别隐含问题。

综合判断时，不要仅按总分机械录用。后端岗位应重点关注：

- 数据正确性和并发安全意识。
- 模块职责、接口边界和可维护性。
- 故障定位是否基于证据，而不是反复猜测。
- 是否理解自己项目中使用的技术，而非只会背诵。
- 使用 AI 工具时是否保留独立判断和验证闭环。

## 三、Java 语言基础与 JVM

### 1. `==`、`equals` 和 `hashCode` 有什么关系

**难度：** 初级

**问题：** Java 中 `==` 与 `equals` 分别比较什么？重写 `equals` 时为什么通常必须重写 `hashCode`？

**考察点：** 对象相等语义、哈希容器契约。

**参考答案：**

- 基本类型使用 `==` 比较值；引用类型使用 `==` 比较是否指向同一对象。
- `Object.equals` 默认等价于引用比较，业务对象可以重写为值相等。
- 如果两个对象 `equals` 为 `true`，它们的 `hashCode` 必须相同，否则放入 `HashMap`、`HashSet` 后可能无法正确查找或去重。
- `hashCode` 相同不代表 `equals` 一定为 `true`，哈希冲突是允许的。
- 参与相等性判断的字段最好在对象作为哈希键期间保持不变。

**深入追问：** 可变对象作为 `HashMap` 的 key，放入后修改参与哈希计算的字段，会发生什么？

**评分要点：** 能指出对象可能仍在原桶位置，按新哈希值查找失败；高级回答应提出不可变 key、值对象或复制键值等方案。

### 2. `ArrayList`、`LinkedList` 和 `HashMap` 如何选择

**难度：** 初级

**问题：** 请比较三者的核心数据结构、常见复杂度和实际选择原则。

**考察点：** 集合使用、复杂度与真实运行成本。

**参考答案：**

- `ArrayList` 基于连续数组，随机访问快，尾部追加通常为摊销 O(1)，中间插入删除需要移动元素。
- `LinkedList` 基于双向链表，已定位节点后的插入删除快，但按索引定位为 O(n)，节点对象多且缓存局部性差。
- `HashMap` 用哈希定位桶，平均查找和写入接近 O(1)；Java 8 中冲突较多时可能由链表树化为红黑树。
- 实际业务中 `ArrayList` 通常比 `LinkedList` 更常用，不能只依据理论上的插入复杂度选择。
- `HashMap` 默认不保证线程安全，也不应依赖其遍历顺序。

**深入追问：** 为什么数据库查询结果通常更适合用 `ArrayList`，即使后面可能删除几个元素？

**评分要点：** 能结合遍历、内存布局、局部性和删除比例回答，而不是机械背复杂度。

### 3. 泛型擦除带来了哪些影响

**难度：** 中级

**问题：** Java 泛型是如何实现的？为什么不能直接 `new T()` 或创建 `new T[10]`？

**考察点：** 类型擦除、编译期类型安全、运行期限制。

**参考答案：**

- Java 泛型主要通过类型擦除实现，泛型参数用于编译期检查，运行时通常不保留具体类型参数。
- 擦除后 `T` 变成其上界或 `Object`，因此运行时无法直接知道如何实例化 `T`。
- 泛型数组会破坏数组运行期类型检查与泛型擦除之间的一致性，所以不能直接创建。
- 可以显式传入 `Class<T>`、构造函数引用、`Supplier<T>` 或使用反射创建实例。
- `List<String>` 与 `List<Integer>` 在运行时通常是同一个原始类型，但字段、父类等位置的泛型签名可能通过反射读取。

**深入追问：** `List<? extends Number>` 和 `List<? super Integer>` 分别适合读还是写？

**评分要点：** 能说明 PECS：生产者用 `extends`，消费者用 `super`，并能举出安全读写范围。

### 4. 受检异常和非受检异常应如何使用

**难度：** 中级

**问题：** 如何区分 checked exception 与 runtime exception？业务异常应该如何设计？

**考察点：** 异常语义、错误边界、接口设计。

**参考答案：**

- 受检异常要求调用方捕获或声明，适合调用方确实能采取恢复动作的场景。
- 非受检异常通常表示编程错误、非法状态或跨层统一处理的业务失败。
- 不应捕获 `Exception` 后静默忽略，也不应在每一层重复记录同一异常。
- 业务异常应包含稳定错误码和安全的用户消息；底层异常可以作为 cause 保留，不能把数据库或堆栈细节直接返回给客户端。
- 应在明确边界统一转换，例如 Web 层异常处理器将领域错误映射为 HTTP 状态和错误响应。

**深入追问：** 日志应该在哪一层记录异常，如何避免同一错误产生多条重复堆栈？

**评分要点：** 中级候选人应能说明“能够完整处理或最终结束请求的边界记录”，并保留关联 ID 和上下文。

### 5. 不可变对象有什么价值，如何实现

**难度：** 中级

**问题：** 为什么在并发和领域建模中常推荐不可变对象？

**考察点：** 状态管理、线程安全、值对象设计。

**参考答案：**

- 不可变对象创建后状态不变化，天然更易共享、缓存、推理和测试。
- 常见做法包括类不可被随意继承、字段为 `private final`、构造时完整校验、不暴露可变内部对象、对集合做防御性复制。
- `final` 只保证引用不能重新赋值，不保证引用指向的对象不可变。
- Java `record` 适合表达数据载体，但如果组件本身是可变集合，仍需防御性复制。
- 复杂业务不应为了“不可变”而复制整个大对象，应根据聚合边界和性能选择。

**深入追问：** `record Order(List<Item> items)` 是否天然不可变？

**评分要点：** 必须指出不是深度不可变，调用者仍可能修改原列表或访问器返回的列表。

### 6. JVM 内存区域和常见内存问题

**难度：** 中级

**问题：** 请说明堆、线程栈、元空间的主要用途，并区分内存泄漏和内存溢出。

**考察点：** JVM 基础、故障分类。

**参考答案：**

- 堆主要存放对象实例，由 GC 管理并被线程共享。
- 每个线程有自己的虚拟机栈，栈帧包含局部变量、操作数栈等；递归过深可能触发 `StackOverflowError`。
- 元空间存放类元数据，使用本地内存；大量动态生成类或类加载器无法回收可能导致元空间耗尽。
- 内存泄漏指对象已无业务价值但仍被引用，最终可能导致 OOM；内存溢出是分配请求无法满足的结果，不一定都是泄漏。
- 排查需要结合 OOM 类型、GC 日志、堆转储、线程和进程指标，而不是直接增加堆内存。

**深入追问：** 一个服务堆使用持续上升，但 Full GC 后明显下降，这一定是泄漏吗？

**评分要点：** 应回答“不一定”，还要观察基线是否逐周期抬升、对象增长来源、流量和缓存策略。

### 7. GC 问题应如何定位

**难度：** 高级

**问题：** 线上服务频繁 Full GC、延迟突增，你会如何定位和处理？

**考察点：** 性能排障方法、证据链。

**参考答案：**

1. 确认现象与影响范围：吞吐、P99、CPU、暂停时间、容器限制、是否刚发布。
2. 查看 GC 日志，识别收集器、分代占用、晋升失败、大对象、分配速率和暂停原因。
3. 检查堆转储或对象直方图，关注占用最大对象、增长趋势和 GC Root 引用链。
4. 将对象来源关联到请求、缓存、批任务或新版本代码。
5. 优先修复无界缓存、一次性加载、对象滞留等根因，再评估堆大小、分代参数或收集器调整。
6. 通过压测、灰度和指标对比验证，避免只靠 JVM 参数掩盖问题。

**深入追问：** 如果没有足够磁盘生成完整 heap dump，还能采集哪些低风险证据？

**评分要点：** 可提及 GC 日志、类直方图、JFR、采样分析、容器指标和有限时段流量对比。

### 8. 类加载机制和类加载器泄漏

**难度：** 高级

**问题：** 双亲委派解决了什么问题？什么情况下会出现类加载器泄漏？

**考察点：** 类隔离、运行容器、热加载问题。

**参考答案：**

- 双亲委派优先让父加载器加载类，避免核心类被重复或恶意替换，并保持类型唯一性。
- 插件、应用服务器、SPI 等场景可能需要打破或调整委派方向，实现模块隔离或由线程上下文类加载器加载实现。
- 类由加载它的类加载器关联，只有类加载器及其加载的所有类都不可达时才可能卸载。
- 静态集合、线程、`ThreadLocal`、驱动注册、定时任务或全局缓存持有应用类，可能导致旧类加载器无法回收。

**深入追问：** 为什么应用热部署后内存不断增加，但普通对象看起来都能被回收？

**评分要点：** 能将现象与旧应用类加载器、存活线程和静态引用链联系起来。

## 四、并发编程

### 9. `volatile` 能保证什么，不能保证什么

**难度：** 中级

**问题：** `volatile` 的可见性和有序性具体指什么？为什么它不能保证 `count++` 的线程安全？

**考察点：** Java 内存模型、原子性。

**参考答案：**

- 对 `volatile` 变量的写入对随后读取该变量的线程可见。
- 它会建立相应的 happens-before 关系并限制特定指令重排序。
- `count++` 包含读取、计算和写回多个步骤，多个线程可能丢失更新，因此 `volatile` 不能让复合操作原子化。
- 可根据场景使用 `AtomicInteger`、`LongAdder`、锁或将状态限制在单线程中。
- `volatile` 适合状态标志、配置快照引用等单次读写即可表达完整状态的场景。

**深入追问：** 为什么发布一个构造完成后不再修改的配置对象时，可以用 `volatile` 引用？

**评分要点：** 能说明安全发布、引用可见性和对象初始化写入对读取线程可见。

### 10. 线程池参数如何设置

**难度：** 中级

**问题：** `ThreadPoolExecutor` 的核心参数有哪些？如何避免线程池把服务拖垮？

**考察点：** 资源治理、背压。

**参考答案：**

- 关键参数包括核心线程数、最大线程数、空闲时间、任务队列、线程工厂和拒绝策略。
- 无界队列可能导致请求堆积和内存耗尽；无限制创建线程可能造成上下文切换、连接争用和系统失稳。
- CPU 密集任务通常接近 CPU 核数；I/O 密集任务可适当增加，但应结合等待比例、下游连接池和压测结果。
- 不同优先级、耗时和下游依赖的任务最好隔离线程池，避免互相拖垮。
- 应监控活跃线程、队列长度、拒绝数、任务耗时，并设计超时、限流、降级和可接受的拒绝策略。

**深入追问：** Web 请求提交异步任务后立即返回，但任务队列已满，你会如何定义接口语义？

**评分要点：** 应讨论拒绝反馈、任务持久化、幂等键和“已接收”与“已完成”的状态区分。

### 11. `synchronized`、`ReentrantLock` 和原子类如何选择

**难度：** 中级

**问题：** 三类同步方式分别适合什么场景？

**考察点：** 锁语义、可维护性。

**参考答案：**

- `synchronized` 语义清晰、自动释放，适合常规互斥临界区。
- `ReentrantLock` 支持可中断获取、尝试锁、公平锁和多个条件队列，但必须在 `finally` 中释放。
- 原子类适合单变量或可表达为 CAS 循环的简单状态更新；复杂多变量不变量通常仍需要锁或重新设计状态模型。
- `LongAdder` 在高竞争计数场景吞吐较好，但读取不是强一致快照，不适合要求精确事务语义的余额。
- 选择应以正确性和可读性优先，不能因为“无锁更快”盲目使用 CAS。

**深入追问：** 两个账户转账时如何避免死锁？

**评分要点：** 能提出稳定锁顺序、超时重试或由数据库原子事务负责，并考虑账户不存在、余额和幂等。

### 12. `ThreadLocal` 的用途和风险

**难度：** 中级

**问题：** `ThreadLocal` 为什么在线程池中容易造成数据串用或内存问题？

**考察点：** 请求上下文、线程复用。

**参考答案：**

- `ThreadLocal` 将值绑定到当前线程，常用于请求追踪、租户上下文等。
- 线程池线程长期复用，如果请求结束未清理，下一个请求可能读取到旧数据。
- `ThreadLocalMap` 的 key 是弱引用，但 value 并不会因此立即释放；线程长期存活时可能形成滞留。
- 应在统一边界使用 `try/finally` 清理，更优方案是显式传递上下文，减少隐藏依赖。
- 异步任务切换线程后不会自动继承普通 `ThreadLocal`，上下文传播必须明确设计。

**深入追问：** 日志 MDC 在异步线程中丢失 trace ID，如何处理？

**评分要点：** 可提出任务装饰器、显式上下文快照与恢复，并确保任务结束清理。

### 13. `CompletableFuture` 常见陷阱

**难度：** 高级

**问题：** 使用 `CompletableFuture` 并行调用多个下游时，需要注意哪些问题？

**考察点：** 异步编排、异常和资源隔离。

**参考答案：**

- 明确使用哪个执行器，避免大量阻塞任务占用公共 `ForkJoinPool`。
- 为每个下游及整体流程设置超时，区分超时、业务失败和取消。
- 正确组合 `thenCompose`、`thenCombine`、`allOf`，避免嵌套 future 或阻塞 `join` 抵消异步价值。
- 设计部分成功、降级和异常聚合语义，不能用 `exceptionally` 静默吞错。
- 传播 trace、租户和安全上下文，同时考虑线程池、HTTP 连接池和下游容量。

**深入追问：** 三个下游中两个成功，一个超时，接口应该返回什么？

**评分要点：** 没有唯一答案，重点看候选人是否根据业务一致性、可降级性和响应契约做选择。

## 五、Spring 与 Web 后端

### 14. IoC 和依赖注入解决了什么问题

**难度：** 初级

**问题：** Spring IoC 容器的核心价值是什么？为什么推荐构造器注入？

**考察点：** 依赖管理、模块边界。

**参考答案：**

- IoC 将对象创建、依赖装配和生命周期管理从业务代码移交给容器。
- 依赖注入使模块依赖显式化，便于替换实现和测试。
- 构造器注入能表达必需依赖，支持不可变字段，避免对象处于未完整初始化状态。
- 字段注入隐藏依赖，不利于单元测试，也容易让类在不知不觉中依赖过多服务。
- 如果构造器参数很多，通常说明职责过多，应先评估模块拆分，而不是用字段注入掩盖。

**深入追问：** 出现循环依赖说明什么？

**评分要点：** 除容器机制外，应指出可能存在职责纠缠，可通过领域事件、接口反转或重新划分服务解决。

### 15. Spring AOP 为什么会出现自调用失效

**难度：** 中级

**问题：** 同一个 Bean 内部方法调用另一个带 `@Transactional` 或 AOP 注解的方法，为什么可能不生效？

**考察点：** 代理机制、调用边界。

**参考答案：**

- Spring AOP 常通过代理对象拦截外部调用。
- Bean 内部使用 `this.method()` 属于直接调用目标对象方法，没有经过代理，因此拦截器可能不执行。
- 可将事务边界提取到另一个职责明确的 Bean，由外部调用代理；也可使用 AspectJ 等不同机制，但不应优先用“获取自身代理”制造隐藏耦合。
- 应同时检查方法可见性、Bean 是否由容器管理和代理类型。

**深入追问：** 把每个方法都拆成一个 Bean 是否合理？

**评分要点：** 应以业务事务边界和职责划分为依据，而不是仅为绕过代理问题机械拆分。

### 16. Spring 事务的传播和回滚边界

**难度：** 中级

**问题：** `REQUIRED` 与 `REQUIRES_NEW` 有什么区别？哪些情况下事务可能没有回滚？

**考察点：** 事务语义、代理和异常处理。

**参考答案：**

- `REQUIRED` 默认加入已有事务，没有则新建；`REQUIRES_NEW` 挂起外层事务并创建独立事务。
- 默认情况下 Spring 通常对未检查异常回滚，受检异常需要根据规则配置。
- 自调用绕过代理、异常被捕获后未重新抛出、方法不在代理边界、数据库引擎不支持事务等都可能导致预期回滚失效。
- `REQUIRES_NEW` 会额外占用数据库连接，外层事务持有连接时，大量嵌套调用可能耗尽连接池。
- 事务边界应围绕业务一致性设计，不宜包住长时间远程调用。

**深入追问：** 数据库提交成功后发送消息失败，单纯扩大本地事务能解决吗？

**评分要点：** 应指出数据库和消息系统不是同一本地事务，可讨论 outbox、事务消息、补偿与幂等消费。

### 17. 如何设计统一 API 错误响应

**难度：** 中级

**问题：** Spring Boot 项目中如何统一处理参数错误、业务错误和系统错误？

**考察点：** API 契约、安全与可观测性。

**参考答案：**

- 使用 Bean Validation 完成输入结构校验，并在统一异常处理器中转换为稳定响应。
- 业务层抛出带错误码的领域异常；系统异常返回通用消息，真实堆栈只记录在服务端。
- 响应通常包含稳定错误码、可读消息、请求或 trace ID，必要时包含安全的字段级错误。
- HTTP 状态码应反映认证失败、权限不足、资源不存在、冲突和服务错误等语义。
- 不应所有错误都返回 HTTP 200，也不应把 SQL、文件路径或敏感配置暴露给客户端。

**深入追问：** 重复提交订单应返回 400、409 还是已有订单结果？

**评分要点：** 允许多种方案，但必须结合幂等协议和客户端重试语义说明。

### 18. 认证、授权和 Cookie/JWT 如何选择

**难度：** 中级

**问题：** 浏览器 Web 应用中，Session Cookie 与 JWT 分别有什么特点？

**考察点：** 身份安全、状态管理。

**参考答案：**

- 服务端 Session 易于主动失效和集中控制，但需要共享会话存储或粘性策略。
- JWT 可离线校验、适合跨服务传递声明，但撤销、轮换、权限即时变更和令牌泄漏处理更复杂。
- 浏览器中令牌放在可被 JavaScript 读取的存储会增加 XSS 窃取风险；`HttpOnly`、`Secure`、适当 `SameSite` 的 Cookie 可降低读取风险，但需要考虑 CSRF。
- 认证只确认“你是谁”，授权还需检查“你能操作什么资源”，不能只在前端隐藏按钮。
- 无论采用何种方式，都需要过期、刷新、登出、密钥轮换、审计和最小权限设计。

**深入追问：** 多租户系统如何防止用户通过修改 URL 访问其他租户数据？

**评分要点：** 必须在后端可信身份上下文中注入租户条件，并在查询、写入和唯一约束层持续隔离。

### 19. Spring Boot 服务如何进行分层和模块化

**难度：** 高级

**问题：** 一个业务持续增长的 Spring Boot 项目，你会按技术层还是业务模块组织代码？

**考察点：** 架构职责、复杂度控制。

**参考答案：**

- 小项目可以使用 Controller、Service、Repository 分层，但业务增长后仅按技术层会让一个功能散落在全项目。
- 更推荐先按业务能力划分模块，再在模块内部设置接口、应用服务、领域逻辑和基础设施适配。
- Controller 负责协议转换，应用服务编排用例，领域逻辑维护业务不变量，Repository 隔离持久化细节。
- 模块间通过明确接口、事件或稳定数据契约协作，避免跨模块直接访问内部表和实现类。
- 架构不是目录命名，应通过依赖规则、测试和代码评审防止边界退化。

**深入追问：** 如果两个模块都需要“用户信息”，是否应该共享同一个 User 实体？

**评分要点：** 高级回答应区分身份主数据、模块视图和上下文边界，避免共享巨型领域对象。

## 六、数据库、缓存与分布式系统

### 20. 数据库索引为什么可能不生效

**难度：** 中级

**问题：** 已经建立索引但查询仍然很慢，你会检查什么？

**考察点：** SQL 与执行计划。

**参考答案：**

- 使用执行计划确认访问类型、估算行数、实际行数、回表、排序和临时表情况。
- 检查联合索引最左前缀、范围条件后的列、对索引列做函数或隐式类型转换、低选择性条件等。
- 检查返回数据量是否过大、是否 `SELECT *`、是否需要覆盖索引、排序与分页是否匹配索引。
- 关注统计信息是否过期、参数分布是否倾斜，以及慢点是否其实来自锁等待或网络。
- 索引会增加写入和存储成本，不能通过“每列都建索引”解决。

**深入追问：** `LIKE '%keyword%'` 为什么通常难以使用普通 B-Tree 索引？

**评分要点：** 能解释前缀未知导致无法按有序索引定位，并提出全文索引或搜索服务等替代方案。

### 21. 事务隔离级别与并发更新

**难度：** 中级

**问题：** 脏读、不可重复读、幻读分别是什么？库存扣减如何避免超卖？

**考察点：** 数据一致性、并发控制。

**参考答案：**

- 脏读是读到未提交数据；不可重复读是同一事务两次读取同一行结果不同；幻读通常指范围查询出现新增或消失的行。
- 库存扣减可以用带条件的原子更新，例如在 `stock >= quantity` 时执行减法，并检查受影响行数。
- 也可以使用悲观锁或带版本号的乐观锁，选择取决于竞争程度和业务流程。
- 仅在应用代码中先查库存再更新，如果没有锁或条件约束，会产生竞态。
- 还要处理重复请求、事务失败、订单取消后的库存释放和消息重复消费。

**深入追问：** 乐观锁冲突后是否应该无限重试？

**评分要点：** 应限制次数、加入退避，并根据用户操作或后台任务决定返回冲突还是重试。

### 22. 深分页为什么慢，如何优化

**难度：** 中级

**问题：** `LIMIT 100000, 20` 为什么可能很慢？

**考察点：** 查询设计、接口语义。

**参考答案：**

- 数据库通常仍需扫描或定位前面大量记录，再丢弃后只返回 20 条。
- 可使用基于稳定排序键的游标分页，例如 `id < lastId`，配合合适索引。
- 如果必须跳页，可先通过覆盖索引取得主键，再回表查询目标数据，或限制最大页数。
- 游标分页需要明确排序唯一性，通常使用时间加 ID 作为稳定游标。
- 数据持续变化时，页码分页本身也可能出现重复或遗漏，接口应明确一致性要求。

**深入追问：** 为什么只用创建时间作为游标可能丢数据？

**评分要点：** 多条记录时间相同会造成边界不唯一，应增加唯一键作为次排序条件。

### 23. 缓存穿透、击穿和雪崩如何治理

**难度：** 中级

**问题：** 请区分三者并给出治理方法。

**考察点：** 缓存稳定性。

**参考答案：**

- 穿透：查询不存在的数据，缓存未命中并持续访问数据库；可缓存空值、校验输入或使用布隆过滤器。
- 击穿：某个热点 key 失效，大量请求同时回源；可使用互斥重建、逻辑过期、提前刷新或请求合并。
- 雪崩：大量 key 同时失效或缓存服务整体不可用；可随机化过期时间、多级缓存、限流降级和高可用部署。
- 所有方案都要考虑数据一致性、空值过期、锁失败和缓存容量。
- 缓存不是事实来源，关键写流程应先定义数据库与缓存的职责。

**深入追问：** 更新数据库后删除缓存失败怎么办？

**评分要点：** 可讨论重试、消息通知、订阅变更、短 TTL、延迟双删的局限，重点是明确可接受不一致窗口。

### 24. 如何设计接口幂等

**难度：** 中级

**问题：** 支付、创建订单或异步任务提交接口如何防止重复执行？

**考察点：** 重试语义、数据约束。

**参考答案：**

- 客户端为一次业务操作生成幂等键，服务端将其与调用方和操作类型绑定。
- 数据库使用唯一约束作为最终防线，不能只依赖先查询后插入。
- 需要保存处理状态和结果，使重复请求返回同一结果，区分处理中、成功和失败是否可重试。
- 幂等键应有生命周期，参数不一致却复用同一键时应拒绝。
- 下游调用和消息消费也要分别实现幂等，入口幂等不能自动覆盖整条链路。

**深入追问：** 第一次请求仍在处理中，第二次请求应返回什么？

**评分要点：** 可同步等待、返回处理中或冲突，但必须有明确契约、超时和查询机制。

### 25. 消息队列如何保证业务最终一致

**难度：** 高级

**问题：** 订单落库后需要发送消息，如何避免“数据库成功但消息丢失”？

**考察点：** 本地事务、消息可靠性。

**参考答案：**

- 在同一本地数据库事务中写业务数据和 outbox 事件表。
- 独立发布器读取未发送事件并投递消息，成功后更新状态；失败可以重试和告警。
- 消费者必须幂等，因为消息系统通常只能实现至少一次投递语义。
- 应处理事件顺序、重复、毒消息、重试退避和人工补偿。
- 也可以使用消息中间件提供的事务消息，但仍要理解其失败窗口和运维复杂度。

**深入追问：** outbox 发布成功但更新“已发送”状态失败会怎样？

**评分要点：** 会重复发送，因此消费者幂等是必要条件，发布端也可使用事件 ID 去重和状态机。

### 26. 分布式锁是否能解决所有并发问题

**难度：** 高级

**问题：** 使用 Redis 分布式锁时有哪些必须考虑的问题？

**考察点：** 租约、故障模型、正确性。

**参考答案：**

- 加锁应使用原子设置并带过期时间，释放时只能删除自己持有的锁，通常使用唯一 token 加 Lua 脚本校验。
- 任务执行时间可能超过租约，需要续期或让业务操作本身具备 fencing token 等防止旧持有者继续写入的机制。
- 网络分区、进程暂停、Redis 故障切换都可能破坏“同一时刻只有一个执行者”的假设。
- 如果数据库唯一约束或原子更新已经能保证正确性，分布式锁可能只是额外复杂度。
- 锁适合协调，但最终数据正确性最好仍由事实存储的约束保障。

**深入追问：** 获得锁后进程暂停，锁过期且其他实例获得新锁，旧进程恢复后会发生什么？

**评分要点：** 能识别双持有者风险，并提出版本号、fencing token 或数据库条件写入。

## 七、工程实践与系统设计

### 27. 如何制定测试策略

**难度：** 中级

**问题：** 一个 Spring Boot 订单服务应该如何分配单元测试、集成测试和端到端测试？

**考察点：** 测试边界、投入产出。

**参考答案：**

- 纯业务规则使用快速、稳定的单元测试覆盖边界值和不变量。
- Repository、事务、SQL、序列化和框架配置使用集成测试验证真实基础设施行为，可用临时数据库或容器。
- 少量端到端测试覆盖最关键用户路径，不应把所有逻辑都依赖昂贵的 E2E 测试。
- 外部服务通过契约测试、可控桩和少量真实环境验证组合处理。
- 测试数据应隔离且可重复，避免依赖执行顺序和共享脏环境。

**深入追问：** Mock 很多但线上仍频繁出错，可能说明什么？

**评分要点：** 可能测试过度贴合实现、缺少真实边界验证、契约不准确或关键业务不变量未覆盖。

### 28. 线上接口突然变慢如何排查

**难度：** 高级

**问题：** 某接口 P99 从 200ms 上升到 5s，但平均延迟变化不大，你会如何处理？

**考察点：** 可观测性、系统排障。

**参考答案：**

1. 明确时间点、影响实例、请求特征和最近变更。
2. 从 trace 分解应用、数据库、缓存、远程调用和队列等待时间。
3. 对比慢请求与正常请求的参数、数据量、租户、SQL 执行计划和下游节点。
4. 检查线程池、连接池、GC、CPU、磁盘、网络、锁等待和限流重试。
5. 必要时先止损：回滚、降级、限流、隔离异常租户或关闭高风险功能。
6. 修复后用监控和回放验证，并补充告警、测试和容量基线。

**深入追问：** 为什么平均值正常不能说明服务正常？

**评分要点：** 能解释长尾被平均值掩盖，用户体验和超时通常由高分位决定。

### 29. 设计一个可扩展的文件导入系统

**难度：** 高级

**问题：** 用户上传十万行 Excel/CSV，系统需要校验、导入并提供错误报告，请给出设计。

**考察点：** 异步任务、状态机、资源控制。

**参考答案：**

- 上传接口只负责鉴权、文件类型与大小检查、存储文件并创建任务，返回任务 ID。
- 后台 worker 流式读取或分批处理，避免整个文件进入内存。
- 任务状态明确区分待处理、处理中、成功、部分成功、失败、取消，并记录进度和统计。
- 校验分为格式校验、字段校验、业务关联校验；错误报告可单独生成并提供限时下载。
- 数据写入按批次事务处理，明确“全有或全无”还是“合法行成功”的业务语义。
- 还需考虑幂等、重复文件、任务重试、并发配额、恶意公式、编码和审计。

**深入追问：** 如果第 80000 行失败，前 79999 行是否保留？

**评分要点：** 没有统一答案，候选人必须先澄清业务原子性，再设计事务和状态。

### 30. 如何评审一个参数不断增加的 Service 方法

**难度：** 高级

**问题：** 某业务方法已有 15 个参数，调用方越来越多，你会直接封装成一个 DTO 吗？

**考察点：** 复杂度来源、模块职责。

**参考答案：**

- DTO 可以改善调用形式，但不一定消除复杂度，可能只是把参数爆发藏进一个“大袋子”。
- 先判断参数是否属于同一个业务概念、是否混入查询条件、权限上下文、配置和执行策略。
- 将稳定值组合为值对象，把调用上下文放在明确边界，将不同用例拆成不同命令或服务。
- 检查方法是否承担校验、查询、计算、持久化、通知等过多职责。
- 重构目标是让数据流单向、依赖清晰和不变量集中，而不是单纯减少参数数量。

**深入追问：** 什么情况下 Command 对象是合理的？

**评分要点：** 当它表达一个稳定用例输入、有明确校验规则且不携带无关依赖时合理。

## 八、前端与前后端协作能力

### 31. 浏览器从发起请求到展示数据经历了什么

**难度：** 初级至中级

**问题：** 前端调用后端 API 时，请说明 DNS、HTTP、浏览器安全限制和页面状态更新中的关键环节。

**考察点：** Web 全链路理解。

**参考答案：**

- 浏览器解析地址、建立 TCP/TLS 连接并发送 HTTP 请求，实际还可能经过代理、CDN、网关和负载均衡。
- 请求携带方法、路径、头、Cookie 和 body，后端返回状态码、响应头和数据。
- 跨源请求受同源策略约束，某些请求会先发送 CORS 预检。
- 前端需要处理加载、成功、空数据、业务失败、网络失败、超时和取消状态。
- 数据进入状态管理后触发组件重新渲染，同时要避免过期响应覆盖新请求结果。

**深入追问：** CORS 错误能否只靠前端代码修复？

**评分要点：** 通常需要服务端或网关返回正确响应头；CORS 是浏览器执行的安全策略，不等同于后端接口不可达。

### 32. React/Vue 中如何管理服务端状态

**难度：** 中级

**问题：** 接口数据是否都应该放进全局状态管理？

**考察点：** 前端状态边界。

**参考答案：**

- 接口缓存属于服务端状态，包含加载、过期、重试、失效和并发请求等语义，可使用 TanStack Query、SWR 或对应生态工具管理。
- 组件交互状态优先保留在最近的组件层级；跨页面共享且确实稳定的客户端状态再进入全局 store。
- 不应把所有请求结果复制到全局状态，容易造成双重事实来源和手动同步问题。
- 更新数据后应根据业务选择失效重查、乐观更新或直接更新缓存，并处理回滚。

**深入追问：** 列表页编辑一条记录后如何保证列表与详情一致？

**评分要点：** 能说明统一缓存 key、局部更新或失效重查，避免两个独立 store 各自维护副本。

### 33. 前端鉴权有哪些常见错误

**难度：** 中级

**问题：** 隐藏无权限按钮是否等于完成授权？前端如何与后端协作处理权限？

**考察点：** 安全边界、用户体验。

**参考答案：**

- 前端权限控制只改善界面体验，真正授权必须由后端对每个受保护操作执行。
- 前端可以根据后端返回的权限声明控制路由、按钮和提示，但不能自行推导出更高权限。
- 401 通常表示未认证或认证失效，403 表示已认证但无权访问，应分别处理。
- 刷新令牌时需要防止多个请求同时刷新、无限重试和旧令牌覆盖新令牌。
- 敏感数据不能因为界面不展示就由接口完整返回。

**深入追问：** 多个请求同时收到 401，如何避免触发多次刷新？

**评分要点：** 可使用单飞机制共享一次刷新 Promise，成功后重放有限请求，失败则统一退出登录。

### 34. TypeScript 能解决什么，不能解决什么

**难度：** 中级

**问题：** 后端已经有 Java DTO，前端 TypeScript 类型是否意味着运行时响应一定正确？

**考察点：** 静态类型与运行时边界。

**参考答案：**

- TypeScript 在编译期检查前端代码，不会自动验证网络返回的 JSON。
- `as SomeType` 只是类型断言，不会改变或校验运行时数据。
- 可通过 OpenAPI 生成客户端类型减少重复，但仍需处理版本兼容、可选字段和错误响应。
- 对关键外部数据可使用运行时 schema 校验；内部可信接口可在成本和风险之间取舍。
- Java 与 TypeScript 的日期、整数范围、枚举和空值语义需要明确约定。

**深入追问：** Java `long` ID 为什么在前端可能需要用字符串传输？

**评分要点：** JavaScript `number` 无法安全表示所有 64 位整数，超过安全范围会丢失精度。

## 九、AI 编程工具使用能力

### 35. 如何让 AI 完成一个真实开发任务

**难度：** 初级至中级

**问题：** 请描述你使用 AI 编程工具完成一个功能的完整流程，而不是只介绍工具名称。

**考察点：** 需求拆解、上下文管理、验证闭环。

**参考答案：**

- 先明确需求、非目标、现有架构、输入输出和验收条件。
- 让工具先读取相关代码和约束，再提出小范围方案；复杂修改应分阶段实施。
- 审查生成的模块职责、数据流、异常处理、安全和依赖，不直接接受大段不可理解代码。
- 运行测试、静态检查和真实场景验证，对失败结果提供最小证据继续修复。
- 最终检查 diff，删除无关修改，记录必要决策，并确保自己能够解释代码。

**深入追问：** 候选人应现场展示一个失败案例，以及如何发现 AI 的错误。

**评分要点：** 真实使用者通常能说明具体上下文、错误、验证证据和调整过程；只说“提高效率很多”不足以证明能力。

### 36. 如何识别 AI 生成代码中的幻觉

**难度：** 中级

**问题：** AI 给出一个看起来合理的新 API 或框架配置，你如何确认它可用？

**考察点：** 事实核验、工程严谨性。

**参考答案：**

- 检查项目实际依赖版本和源码中的现有调用方式。
- 查询官方文档、API 签名、变更记录或本地类型提示，而不是继续让 AI 自证。
- 编写最小可运行验证，执行编译、测试或启动检查。
- 对涉及数据迁移、权限、并发和删除操作的代码提高审查级别。
- 如果工具引用不存在的文件、方法或配置，应回到事实来源重新定位。

**深入追问：** 为什么“代码能编译”仍不足以证明正确？

**评分要点：** 编译只能覆盖部分结构问题，无法证明业务语义、并发、安全、性能和失败路径正确。

### 37. 如何安全地向 AI 提供项目上下文

**难度：** 中级

**问题：** 哪些内容不应直接发送给外部 AI 服务？如何在效率与安全之间取舍？

**考察点：** 数据安全、合规意识。

**参考答案：**

- 不应上传真实密钥、令牌、客户隐私、生产数据库内容、未脱敏日志和受限制源码。
- 使用 `.env` 隔离秘密，对日志和样例数据脱敏，只提供完成任务所需的最小上下文。
- 了解组织批准的工具、数据保留和模型训练策略；敏感项目可使用企业版、私有部署或关闭相关数据使用选项。
- AI 生成的依赖、许可证和代码来源也需要审查。
- 一旦秘密可能泄露，应轮换而不是仅从聊天记录删除。

**深入追问：** 如果候选人曾把生产错误日志直接粘贴给 AI，应继续问其中是否包含 Cookie、Token、手机号或订单数据，以及如何补救。

**评分要点：** 应具备最小披露、脱敏和凭据轮换意识。

### 38. AI 代码评审应该关注什么

**难度：** 高级

**问题：** AI 可以辅助 review，但为什么不能把“AI 已审查”当作合并依据？

**考察点：** 责任边界、评审方法。

**参考答案：**

- AI 适合发现重复模式、遗漏测试、常见安全问题和解释复杂 diff，但它可能缺少业务上下文或产生错误判断。
- 评审仍需确认需求是否满足、模块职责是否合理、数据迁移是否安全、失败和回滚路径是否完整。
- 关键改动应有自动化测试、运行证据和领域负责人确认。
- 给 AI 的评审范围应明确，例如只检查并发、权限或兼容性，避免泛泛输出大量低价值建议。
- 最终责任属于提交者和评审者，不能转移给工具。

**深入追问：** 如何判断 AI review 建议值得采纳？

**评分要点：** 建议应能对应具体代码、可复现风险、项目约束和验证方式，而不是只凭措辞自信。

## 十、项目经历核验题

### 39. 选择一个最熟悉的 Java 项目进行端到端说明

**难度：** 全级别

**问题：** 请从一个用户请求开始，说明它经过哪些模块、数据存储和外部系统，最终如何返回结果。

**考察点：** 项目真实性、系统全貌、个人职责。

**参考答案判断：**

- 候选人应能说清入口、核心模块、数据库、缓存、消息和部署边界。
- 能说明自己负责的具体代码、决策和故障，而非始终使用“我们做了”。
- 能解释至少一个失败路径和一个数据一致性问题。
- 高级候选人应能指出现有设计的不足及演进方案。

**深入追问：** 选择其中一个请求，让候选人画出调用链、事务边界和关键数据变化。

**评分要点：** 细节应前后一致；如果技术名词很多但无法说明数据如何变化，应谨慎判断。

### 40. 描述一次最困难的线上故障

**难度：** 中级至高级

**问题：** 故障最初现象是什么？你收集了什么证据？排除了哪些假设？最终如何修复并防止复发？

**考察点：** 排障过程、责任意识、复盘质量。

**参考答案判断：**

- 好的回答包含时间线、影响、指标或日志证据、根因、止损、修复和后续措施。
- 应区分相关性与因果关系，避免“重启后好了，所以是内存问题”式结论。
- 能坦诚说明误判及如何修正，比塑造从不犯错更可信。

**深入追问：** 如果回到故障发生前，会增加哪一个监控或保护机制？

**评分要点：** 观察候选人能否把一次事故转化为系统性改进。

## 十一、现场编码与设计题

### 41. 编码题：实现并发安全的库存扣减服务

**难度：** 中级

**题目：** 给出商品 ID、扣减数量和幂等键，实现库存扣减核心流程。可以使用伪代码、Java 和 SQL。

**最低要求：**

- 校验数量为正数。
- 使用数据库条件更新或明确锁策略，避免先查后改造成超卖。
- 使用唯一约束或幂等记录处理重复请求。
- 清晰区分库存不足、重复请求和系统失败。
- 有对应的并发测试思路。

**优秀表现：**

- 定义幂等处理中、成功、失败状态。
- 说明事务边界和死锁重试策略。
- 考虑同一幂等键携带不同参数、超时重试和审计。
- 代码模块职责清晰，没有把 Controller、SQL、重试和响应拼在一个方法里。

### 42. 设计题：订单创建与异步履约

**难度：** 高级

**题目：** 设计一个订单创建接口。订单保存后要异步调用库存、通知和报表系统，并允许用户查询进度。

**候选人需要说明：**

1. API 请求与响应契约。
2. 订单和任务状态机。
3. 数据库事务边界。
4. 消息可靠性和消费者幂等。
5. 部分失败、重试、取消和人工补偿。
6. 日志、指标、trace 与告警。
7. 前端如何展示处理中、失败和重试状态。

**优秀表现：** 先澄清一致性要求和规模，再选择方案；不会默认所有步骤必须同步完成，也不会用一个分布式事务掩盖所有业务状态。

## 十三、常见风险信号

以下信号需要结合全场表现判断，不能凭单项直接否定候选人：

- 只背术语，无法说明实际请求、数据和失败路径。
- 把所有性能问题归结为加缓存、加线程或扩容。
- 认为使用事务注解即可解决跨系统一致性。
- 只关注正常流程，不考虑重复请求、超时、取消和部分失败。
- 把前端隐藏按钮当作权限控制。
- 无法解释自己提交的 AI 生成代码，也没有运行测试或核对 API。
- 将生产密钥、客户数据和完整日志直接提供给公共 AI 工具。
- 面对证据冲突时不断更换猜测，却不收集日志、指标、trace 或最小复现。
